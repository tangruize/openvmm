Source-grounded representation account for the staging publish rename boundary.

The production caller is `StagingDirectory::publish` in
`openvmm/openvmm_helpers/src/snapshot/publish.rs`. Its executable body obtains
the current staging path, calls
`rename_no_replace(staging_path, destination).with_context(...)`, retires
`self.path` only after that call returns success, and then returns `Ok(())`.
A failure through the `?` returns before `self.path = None`, so the staging
owner remains present for rollback or drop cleanup.

The production callee is `rename_no_replace` in
`openvmm/openvmm_helpers/src/snapshot/fs.rs`. On
`cfg(all(target_os = "linux", target_env = "gnu"))`, it checks that the source
and destination have the same parent, requires both paths to have file names,
opens the destination parent, and calls `nix::fcntl::renameat2` with
`RenameFlags::RENAME_NOREPLACE`. On other cfgs, the current helper delegates to
`fs_err::rename`. The proof account therefore cannot claim a discharged
portable no-replace filesystem theorem for every target from this fragment
alone. It can only state the source-shaped Linux-GNU no-replace intent and keep
platform fallback semantics as an open resource dependency.

`Context::with_context` is represented as a formatting/context wrapper that
preserves the `Ok`/`Err` shape of the underlying result. This is enough for the
publish body obligation: a successful rename result is the only path to
retiring the staging owner, and an error result stays before commitment and
leaves the staging owner path unchanged.

The repaired proof-side interface in `proofs/snapshot.rs` now makes that
boundary explicit through `rename_no_replace_view`, the concrete
`Result<T, Error>::with_context` result-shape postcondition, and the
`StagingDirectory::publish` postconditions for unchanged failure state. The
remaining completeness question is still intentionally nondeterministic with
respect to the checker observation: two calls with the same `Path` values can
see different filesystem states or races that are not parameters of
`StagingDirectory::publish`. A deterministic proof would need an explicit
filesystem/resource state interface and platform-specific no-replace contract,
not an assumption that every rename succeeds.
