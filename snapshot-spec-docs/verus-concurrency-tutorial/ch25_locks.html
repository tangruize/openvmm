Sharing data with a lock

This chapter solves the same kind of problem as the previous one, with a lock instead of an atomic variable. It is written so that you can read it before or after chapter 24.

The problem

We still want a shared window [lo, hi] with the rule lo <= hi, used by many threads.

An atomic variable holds one machine word, and one atomic instruction changes one variable. Some jobs are bigger than that:

  • changing two fields together, such as replacing the whole window with a new [a, b];
  • reading two fields together, so that you get a consistent pair.

For these jobs the usual tool is a lock. A thread that holds the lock may read and change the protected data; everyone else waits until it is released.

The idea

The idea is the same as in the last chapter: there is a rule that must hold whenever nobody is using the data. What differs is how long you may keep the data.

  • With an atomic, you borrow the key for one atomic step.
  • With a lock, you borrow the data for as long as you hold the lock, which can be many steps.

While you hold the lock, nobody else can look at the data. So you are allowed to break the rule in the middle of your work. The only requirement is that the rule holds again when you release the lock. Verus checks the rule at that moment, not before.

The lock in vstd

vstd provides RwLock<V, Pred>. It holds a value of type V, and Pred names the rule:

  • lock.acquire_write() gives you the data itself, plus a handle, and lets you assume that the rule holds.
  • handle.release_write(new_data) puts the data back. It requires that the rule holds for new_data.
  • lock.acquire_read() gives a read-only handle; handle.borrow() gives a reference to the data, and handle.release_read() gives the lock back.

Where is the permission, the key from chapter 24? It is inside the lock. vstd’s RwLock keeps it there and uses it for you, so you never see it. The rule written on the lock plays the role of the box’s rule.

The rule has a slightly different shape. Instead of the two-input InvariantPredicate, the lock uses its own RwLockPredicate<V> whose function takes self and the data. Here self is the label value, so it can carry configuration:

#![allow(unused)]
fn main() {
pub struct Window {
    pub lo: u64,
    pub hi: u64,
}

pub struct LoLeHi;

impl RwLockPredicate<Window> for LoLeHi {
    open spec fn inv(self, w: Window) -> bool {
        w.lo <= w.hi
    }
}

type Lock = RwLock<Window, LoLeHi>;
}

Read the impl line as: “LoLeHi is the name of a rule for locks that hold a Window. The rule says lo <= hi.” The last line gives a short name to the lock type.

The operations

Here are the two widening operations from chapter 24, written with the lock. The code inside is ordinary Rust. Only the beginning and the end are new:

#![allow(unused)]
fn main() {
// lo = min(lo, n)
pub fn widen_down(lock: &Lock, n: u64) {
    let (mut w, handle) = lock.acquire_write();
    // we may assume lo <= hi here
    if n < w.lo {
        w.lo = n;
    }
    // we must show lo <= hi again before releasing
    handle.release_write(w);
}
}
#![allow(unused)]
fn main() {
// hi = max(hi, n)
pub fn widen_up(lock: &Lock, n: u64) {
    let (mut w, handle) = lock.acquire_write();
    if n > w.hi {
        w.hi = n;
    }
    handle.release_write(w);
}
}

The comparison “is n smaller than lo?” and the update are one critical section, so nobody can change lo between them. With atomics, fetch_min did that job. With a lock you can write the if by hand, because the lock makes the read, the decision and the write one step.

So “widen to contain n” can be written directly:

#![allow(unused)]
fn main() {
// Widen the window so that it contains n. Here a plain if / else-if is fine: the lock makes
// "read, decide, write" one critical section, so the decision cannot go stale. (With atomics,
// the fetch_min / fetch_max instructions play this role; see my_atomic_two_vars.rs.)
pub fn widen(lock: &Lock, n: u64) {
    let (mut w, handle) = lock.acquire_write();
    if n < w.lo {
        w.lo = n;
    } else if n > w.hi {
        w.hi = n;
    }
    handle.release_write(w);
}
}

An operation that atomics cannot do

Now an operation that replaces the window with a new [a, b], where a <= b:

#![allow(unused)]
fn main() {
// EXTRA (not in my_atomic_two_vars.rs): replace the window with [a, b].
pub fn reset_to(lock: &Lock, a: u64, b: u64)
    requires
        a <= b,
{
    let (mut w, handle) = lock.acquire_write();
    w.lo = a;
    // lo <= hi is BROKEN here if a > the old hi (e.g. [20, 30] -> lo = 50 gives [50, 30]).
    // Under the lock nobody else can see this state, so it is fine.
    w.hi = b;
    // lo = a <= b = hi: the invariant holds again, and release_write checks exactly that.
    handle.release_write(w);
}
}

Look at the moment after w.lo = a. If the old window was [20, 30] and a is 50, the data is [50, 30]: the rule is broken. Nobody can see this, because we still hold the lock. After w.hi = b the rule holds again, and release_write checks exactly that.

With two separate atomic variables this operation is not safe as two independent writes. Each write is its own step, and another thread could run in between and see [50, 30]. (There are other ways to do it with atomics, such as packing both values into one word, but not as two plain writes.)

Running it

Threads share the lock through an Arc, as in chapter 24:

#![allow(unused)]
fn main() {
fn spawn_widen_down(lock: &Arc<Lock>, n: u64) -> (h: JoinHandle<()>) {
    let lock = lock.clone();
    spawn(move || -> (r: ()) { widen_down(&lock, n) })
}
}

When the threads are done, the parent reads both fields inside one critical section:

#![allow(unused)]
fn main() {
    // Both fields are read in one critical section, so they are consistent.
    let handle = lock.acquire_read();
    let w = handle.borrow();
    let result = (w.lo, w.hi);
    handle.release_read();
    result
}

The function promises out.0 <= out.1, and this time the promise is about two numbers the program really holds. In chapter 24 the final claim could only be made in proof mode. The reason is the lock: while we hold the read handle, nobody can change either field.

The same thing with Rust’s own lock

Verus code looks a little different from ordinary Rust code. Here is the same window with std::sync::RwLock, in plain Rust:

#![allow(unused)]
fn main() {
fn widen_down(lock: &RwLock<Window>, n: u64) {
    let mut w = lock.write().unwrap(); // guard: blocks until we hold the lock
    if n < w.lo {
        w.lo = n;
    }
} // the guard is dropped here, and that releases the lock automatically
}

The differences:

std::sync::RwLockvstd::rwlock::RwLock
acquirewrite(), read()acquire_write(), acquire_read()
what you geta guard that behaves like a reference to the datathe data by value, plus a handle
releaseautomatic, when the guard goes out of scopeexplicit: release_write(data)
errorsreturns a Result (the lock can be “poisoned”)no Result
waitingthe thread sleepsthe thread spins

The explicit release is not an accident. At release, Verus must see you prove the rule. A function can carry that as a requires. A destructor, which runs when a guard is dropped, cannot require anything of the caller. So vstd’s lock makes the release a function call.

The Rust code you write between acquire and release stays the same. Only the edges change.

When the rule is broken at release

Remove the line w.hi = b; from reset_to. Now the data is left as [a, old_hi], which may break the rule. Verus rejects the program at the release:

error: precondition not satisfied
  --> reset_to.rs:87:5
   |
87 |     handle.release_write(w);
   |     ^^^^^^^^^^^^^^^^^^^^^^^
   |
  --> vstd/rwlock.rs:405:12
   |
   = note: failed precondition

The failed precondition is release_write’s requires: the rule must hold for the data being put back. Everything before that line was allowed.

What is and is not proved

  • Whenever the lock is free, the window satisfies lo <= hi.
  • Verus does not check that you release the lock. A handle is not released when it is dropped, and a forgotten release_write would hang the program. So this proves the rule, not the absence of deadlock.
  • vstd’s lock waits by spinning, which is simple but can be slow when many threads compete.
  • vstd has no specification for std::sync::Mutex. The vstd lock is a replacement, not a wrapper, so verifying code that already uses std locks means either switching to the vstd lock or writing a trusted specification yourself.
