Sharing an atomic variable with an invariant

In the last chapter every thread had its own data. Now the threads will write to the same variable at the same time. That is what makes concurrency hard to verify, and this chapter introduces the tool that handles it: the atomic invariant.

This chapter and the next one (locks) are independent. Read them in either order.

The problem

Keep the window [lo, hi] from the last chapter, but now picture a sensor that reports readings from many threads. The program keeps the smallest and the largest reading seen so far in two shared variables, lo and hi. We want to prove that lo <= hi always holds, whatever order the threads run in.

We start with an even simpler variable: a counter that always changes by 2. We want to prove that the counter is always even.

Background: how threads share and change data in Rust

Rust normally allows many readers or one writer, never both at once. Sharing a value between threads means putting it in an Arc (an atomically reference-counted pointer). But an Arc shares ownership, not the right to change the value: through an Arc you only get a shared reference, which is read-only.

To change a shared value, the value’s type must have interior mutability, which means it can be changed through a shared reference. Rust offers three kinds:

  • an atomic type such as AtomicU64: each operation is one indivisible hardware step;
  • a lock (Mutex, RwLock): one thread at a time may change the data (next chapter);
  • Cell and RefCell: not safe across threads.

This chapter uses atomics. Verus wraps Rust’s atomics in types such as PAtomicU64.

Why Verus needs something new

With one owner, Verus knows the value of a variable by following ownership: a &mut reference means nobody else can change it, so the value before and after a call can be written in a specification.

A shared atomic is different. Any thread can change it at any moment. So a specification cannot say “the counter is 5”, because it may no longer be 5 a moment later.

What a specification can say is something that is true in every state: “the counter is even”. Such a statement is called an invariant. If every step that changes the variable keeps the statement true, then it is true whenever anyone looks.

The idea: a key and a box

Verus models this with two things.

  • The permission is a proof-only key to the variable. You cannot touch the real variable without holding its key. There is only one key, and it cannot be copied.
  • The atomic invariant is a shared box with a rule written on it. The key sits in the box.

To change the variable, a thread takes the key out of the box, changes the variable with one atomic operation, and puts the key back. When the key goes back in, Verus checks that the rule still holds. If it does not, the program does not verify.

Because the key is only ever out of the box for one atomic step, and one atomic step cannot be interrupted, no other thread ever sees a half-finished change.

The key and the box exist only while Verus checks the program. They are erased when the program is compiled, so they cost nothing at run time.

The rule: InvariantPredicate

The rule on the box is written as a function. This is the whole definition, from vstd:

#![allow(unused)]
fn main() {
pub trait InvariantPredicate<K, V> {
    spec fn inv(k: K, v: V) -> bool;
}
}

It says: there is a function inv that takes a k and a v and answers true or false. True means “the box is acceptable”.

  • V is the type of what sits in the box. It is the variable part: every time the box is opened and closed, a possibly different V is put back.
  • K is a constant: one value of any type, given when the box is created and never changed afterwards. Anyone may read it without opening the box. It is the first input of inv, and that is all it is for. Typically it holds ids. (A way to remember it: K for Constant, V for Variable.)

A box needs a name for its rule. We use an empty struct as a label, and write the rule inside an impl:

#![allow(unused)]
fn main() {
pub struct EvenInv;

impl InvariantPredicate<int, PermissionU64> for EvenInv {
    open spec fn inv(x_id: int, perm: PermissionU64) -> bool {
        &&& perm@.patomic == x_id  // the permission belongs to our atomic variable
        &&& perm@.value % 2 == 0  // the property we care about
    }
}

type Inv = AtomicInvariant<int, PermissionU64, EvenInv>;
}

Read the impl line as: “EvenInv is the name of a rule for boxes whose constant is an int and whose contents are a PermissionU64. Here is the rule.”

This rule says two things. The key belongs to our variable (perm@.patomic == x_id), and the value is even (perm@.value % 2 == 0). The first line is bookkeeping that ties the key to the variable. The second is the property we care about.

The last line, type Inv = ..., gives a short name to the box’s type. The box type mentions all three parts: AtomicInvariant<constant type, contents type, label>.

The variable and its key

PAtomicU64::new(v) creates the real atomic variable and, at the same time, its key:

#![allow(unused)]
fn main() {
    let (x, Tracked(perm)) = PAtomicU64::new(0);
    let tracked inv = Inv::new(x.id(), perm, 1);
    let x = Arc::new(x);
    let inv = Arc::new(Tracked(inv));
}
  • The two Arc lines at the end only prepare the variable and the box for sharing; they are explained in the section on sharing below.
  • Tracked(...) marks a proof-only value that Verus tracks so that it cannot be copied.
  • x.id() is the variable’s id, and perm@.patomic is the id of the variable the key belongs to. The rule above says these must match.
  • Inv::new(x.id(), perm, 1) creates the box. It takes the constant (the id), the contents (the key), and a number called the namespace, which you can ignore for now.

Creating the box checks that the rule holds for the starting contents: the value 0 is even.

Every operation on the variable takes the key as an argument, written Tracked(&mut perm). That is how Verus makes sure nobody touches the variable without holding the key.

An operation: one atomic step

Here is the operation “add 2”, using the hardware instruction fetch_add:

#![allow(unused)]
fn main() {
// One physical step (fetch_add), so one open/close of the invariant.
pub fn add_two(x: &PAtomicU64, Tracked(inv): Tracked<&Inv>)
    requires
        inv.constant() == x.id(),
{
    open_atomic_invariant!(inv => perm => {
        x.fetch_add_wrapping(Tracked(&mut perm), 2);
    });
}
}
  • The requires line says that this box is the box for this variable x. We need it because the rule talks about the id in the constant.
  • open_atomic_invariant!(inv => perm => { ... }) takes the key out of the box and calls it perm inside the braces. At the closing brace the key goes back, and Verus checks the rule.
  • Only one atomic operation is allowed between the braces. That is what makes the opening safe, as explained above.

Where is the proof? There is none. At the closing brace Verus must show that the new value is even. It knows two things: the old value was even (the rule, assumed when the box was opened), and the instruction added 2 (the instruction’s specification). Adding 2 to an even number gives an even number, and Verus’s solver sees that on its own.

Another operation, “reset to 0”, uses store:

#![allow(unused)]
fn main() {
// One physical step (store), so one open/close of the invariant.
pub fn reset(x: &PAtomicU64, Tracked(inv): Tracked<&Inv>)
    requires
        inv.constant() == x.id(),
{
    open_atomic_invariant!(inv => perm => {
        x.store(Tracked(&mut perm), 0);
    });
}
}

Sharing the variable and the box between threads

To give every thread the variable and the box, each goes into an Arc, and every thread gets its own clone of both. (The Arc is plumbing; it is not part of the idea.)

#![allow(unused)]
fn main() {
fn spawn_adder(x: &Arc<PAtomicU64>, inv: &Arc<Tracked<Inv>>) -> (h: JoinHandle<()>)
    requires
        inv@.constant() == x.id(),
{
    let (x, inv) = (x.clone(), inv.clone());
    spawn(move || -> (r: ()) { add_two(&x, Tracked(inv.borrow())) })
}
}

The parent starts the threads, waits for all of them, and then reads the counter by opening the box once more:

#![allow(unused)]
fn main() {
    if ok {
        let result;
        open_atomic_invariant!(inv.borrow() => perm => {
            result = x.load(Tracked(&perm));
        });
        Ok(result)
    } else {
        Err(())
    }
}

The function run_threads promises out.unwrap() % 2 == 0. It can promise this because load returns the value inside the key, and the rule says that value is even. The parent never needed to know how many threads ran, or in which order.

When the rule is broken

Change the operation to add 1 instead of 2. Verus rejects the program:

error: Cannot show invariant holds at end of block
  --> f24.rs:41:5
   |
41 | /     open_atomic_invariant!(inv => perm => {
42 | |         x.fetch_add_wrapping(Tracked(&mut perm), 1);
43 | |     });
   | |______^

The message points at the whole block, because that is where the key goes back. The step itself is fine. What fails is the promise made at the end: the new value might be odd. When you see this message, compare the rule with the value the block leaves behind.

Two variables

Now the window: two variables, lo and hi, with the rule lo <= hi.

A rule can only talk about what is in its own box. So to relate two variables, one box holds both keys. Its constant holds two ids, and its contents are two permissions:

#![allow(unused)]
fn main() {
pub struct K {
    pub lo_id: int,
    pub hi_id: int,
}

pub struct V {
    pub lo: PermissionU64,
    pub hi: PermissionU64,
}

// A permission is linear: each one lives in exactly one invariant, so we cannot also
// give `lo` or `hi` its own separate invariant. Properties of a single variable
// (e.g. `lo <= 100`) are simply extra clauses in this joint predicate.
pub struct WindowInv;

impl InvariantPredicate<K, V> for WindowInv {
    open spec fn inv(k: K, v: V) -> bool {
        &&& v.lo@.patomic == k.lo_id
        &&& v.hi@.patomic == k.hi_id
        &&& v.lo@.value <= v.hi@.value  // the relation between the two variables
    }
}

type Inv = AtomicInvariant<K, V, WindowInv>;
}

Notice the comment above the label: a key lives in exactly one box, so lo cannot also get a box of its own. A property of just one variable, such as lo <= 100, becomes an extra line of this rule.

The operations touch one variable each. They use fetch_min and fetch_max, which are single hardware instructions that store the smaller (or larger) of the old value and the argument:

#![allow(unused)]
fn main() {
// One physical step (fetch_min on lo), so one open/close of the invariant.
pub fn widen_down(lo: &PAtomicU64, Tracked(inv): Tracked<&Inv>, n: u64)
    requires
        inv.constant().lo_id == lo.id(),
{
    open_atomic_invariant!(inv => v => {
        let tracked V { lo: mut lo_perm, hi: hi_perm } = v;
        lo.fetch_min(Tracked(&mut lo_perm), n);
        proof {
            v = V { lo: lo_perm, hi: hi_perm };
        }
    });
}
}
#![allow(unused)]
fn main() {
// One physical step (fetch_max on hi), so one open/close of the invariant.
pub fn widen_up(hi: &PAtomicU64, Tracked(inv): Tracked<&Inv>, n: u64)
    requires
        inv.constant().hi_id == hi.id(),
{
    open_atomic_invariant!(inv => v => {
        let tracked V { lo: lo_perm, hi: mut hi_perm } = v;
        hi.fetch_max(Tracked(&mut hi_perm), n);
        proof {
            v = V { lo: lo_perm, hi: hi_perm };
        }
    });
}
}

Each operation opens the same shared box and gets both keys. It uses one and puts both back.

Why does this keep lo <= hi? Because each step moves its variable in the safe direction: lo only goes down and hi only goes up.

fetch_min does the comparison “is n smaller than lo?” and the update as one indivisible step. You could be tempted to write the comparison yourself, with a load followed by a store. Do not: another thread could change lo between your two steps, and your decision would be stale.

An operation that does both, widen the window to contain v, is just the two steps in order:

#![allow(unused)]
fn main() {
// Widen the window so that it contains v: two physical steps, each one safe by itself.
// The fetch_min / fetch_max instructions ARE the "if v < lo" / "if v > hi" checks, done
// atomically; writing `load` then `store` by hand would let the decision go stale.
// At most one of the two steps changes anything (v < lo implies v < hi, and so on), so
// from the outside this behaves like one step, but the invariant proof does not need that.
pub fn widen(lo: &PAtomicU64, hi: &PAtomicU64, Tracked(inv): Tracked<&Inv>, v: u64)
    requires
        inv.constant().lo_id == lo.id(),
        inv.constant().hi_id == hi.id(),
{
    widen_down(lo, Tracked(inv), v);
    widen_up(hi, Tracked(inv), v);
}
}

This is two atomic steps, each safe by itself. At most one of them changes anything (if v is below lo, it is also below hi), so from the outside it looks like one step. The proof does not need that fact, though. It only needs each step to keep the rule.

Reading both variables

With two variables there is one thing you cannot do: read both in a single atomic step. After the threads are done, the program can load lo and load hi, but another thread could have changed one of them in between. So the final claim lo <= hi is stated in proof mode, as a fact about the two keys, by opening the box inside a proof block:

#![allow(unused)]
fn main() {
    // Exec code cannot read two atomics in one atomic step, so the relation is stated
    // about the ghost permissions, in proof mode, by opening the invariant there.
    let Tracked(credit) = vstd::invariant::create_open_invariant_credit();
    proof {
        open_atomic_invariant_in_proof!(credit => inv.borrow() => v => {
            assert(v.lo@.value <= v.hi@.value);
        });
    }
}

It is a true statement, but a weaker one than the single-variable case: it is about the proof-only keys, not about two numbers the program holds. The next chapter shows how a lock gives you a statement about real values.

Several steps: a compare-and-swap loop

Suppose “add 2” were not one hardware instruction. A standard technique builds an update from a compare-and-swap:

  1. read the current value;
  2. compute the new value;
  3. ask the hardware to write the new value only if the variable still holds what you read;
  4. if someone changed it in the meantime, go back to step 1.

compare_exchange_weak(perm, expected, new) is the hardware operation in step 3. It returns Ok(_) if the swap happened and Err(latest_value) if not. (“Weak” means that it may sometimes fail even when the value matched; in a retry loop that is harmless.)

Here is “add 2” written that way. It has several atomic steps, so it opens the box once for each step:

#![allow(unused)]
fn main() {
// Add 2 with a compare-and-swap loop.
pub fn add_two(x: &PAtomicU64, Tracked(inv): Tracked<&Inv>)
    requires
        inv.constant() == x.id(),
{
    // step 1: read the current value
    let mut curr;
    open_atomic_invariant!(inv => perm => {
        curr = x.load(Tracked(&perm));
    });

    loop {
        let next = curr.wrapping_add(2);
        // step 2: swap `next` in, but only if the value is still `curr`
        let res;
        open_atomic_invariant!(inv => perm => {
            res = x.compare_exchange_weak(Tracked(&mut perm), curr, next);
        });
        match res {
            Ok(_) => {
                return ;
            },
            // somebody changed the counter first: `new` is its latest value, try again
            Err(new) => {
                curr = new;
            },
        }
    }
}
}

Between the first step and the second, other threads may run and change the counter. That is fine, because the rule is about every state, and each step keeps it.

Notice something about this function: it opens the box itself. So it is written for this box and this rule, and it can only be used by programs that keep the key in this box. Chapter 27 shows what to do when a function must work for owners whose boxes it cannot see.

Small notes

  • Namespaces. The number given to Inv::new (the 1 above) is a namespace. Verus uses it to forbid opening a box while it is already open, which would let one thread hold the key twice. It only matters when boxes nest, so you can pick any number for now.
  • Other uses of the rule. InvariantPredicate is not specific to the atomic box. vstd also uses it for LocalInvariant (a box that cannot be shared between threads), inside RwLock, and in atomic_ghost.
  • Why Arc<Tracked<Inv>>. Threads need to own what they share, so the box goes in an Arc like the variable. In chapter 26 we will use Shared, vstd’s tracked equivalent.

What is and is not proved

  • In every state that any thread can observe, the rule holds. The final reads prove it for the end of the program.
  • Nothing is claimed about which value the counter has, only that it is even.
  • All of this relies on vstd’s atomic wrappers being correct. Their specifications are trusted, not proved.
  • Only sequentially consistent atomics are modeled.
