Ghost resources: recording what happened

This chapter builds on chapter 24 (atomic invariants). You do not need chapter 25.

The problem

Two threads each add 1 to a shared counter that starts at 0. When both have finished, the parent wants to prove: the counter is exactly 2.

To a human this is obvious. Two threads each added 1, so the counter is 2.

Two kinds of property

The rules in chapters 24 and 25 were about states: “the counter is even”, “lo <= hi”. A rule like that holds in every state, so a rule on the box is enough.

“The counter is exactly 2” is different. It is a fact about history: it holds because two particular additions happened. The same counter value, 1, could come from thread A adding or from thread B adding, and the value alone cannot tell you which one. A rule that only looks at the counter cannot express it.

Why Verus does not see it by itself

Verus checks each thread on its own, plus the box. It has no built-in idea that “thread A’s add has happened” or that “thread B’s add has happened”.

Chapter 23 said that after join, the parent knows only what the thread’s ensures clause says. A thread cannot write “I added 1 to the counter” in its ensures, because (chapter 24) a specification cannot mention a shared value.

So the fact has to travel in some other way: as a proof-only object that the thread returns.

The idea: tickets

Think of a coat-check. Each thread holds a ticket. A ticket says either “I have not added yet” or “I have added”.

  • A thread swaps its ticket from “not yet” to “added” in the same atomic step as its real add.
  • The box keeps a rule: the counter equals the number of “added” tickets.
  • When a thread finishes, it hands its ticket back to the parent.

At the end the parent holds two tickets, and both say “added”. The box’s rule then gives counter == 1 + 1 == 2.

A thread cannot cheat. It cannot change its ticket without really adding (the rule would fail when the key goes back), and it cannot add without changing its ticket (the rule would fail the other way). Verus enforces both.

What a ticket is: FracGhost

In vstd, a ticket is a value of type FracGhost. It records:

  • a ghost number: a number that exists only in the proof. We use 0 for “not added” and 1 for “added”;
  • a fraction of ownership of that number, between 0 (exclusive) and 1.

The rule that makes tickets work: the number can only be changed by someone holding all of the ownership, a fraction of exactly 1. A holder of just a half can read the number but cannot change it.

A ticket can be split into two halves, and two halves can be combined again. We give each thread one half of its ticket and keep the other half in the box. Only inside the box, where a thread can combine its half with the box’s half, can the number change.

All the operations on tickets (every one exists only in the proof). Here t is any ticket:

meaning
t.id()which ghost number this ticket belongs to
t@the number’s current value
t.frac()how much ownership this ticket gives (more than 0, at most 1)
FracGhost::new(v)a new ghost number with value v and ownership 1 (all of it)
t.split()cut t into two halves with the same id and value
t.split_to(f)like split, but the new ticket gets fraction f
t.combine(other)merge other into t; the fractions add up (same id required)
t.update(v)change the value to v; allowed only when t.frac() == 1
t.update_with(other, v)update through two tickets whose fractions add up to 1
t.agree(&other)two tickets with the same id have the same value
t.bounded()a fraction is always in (0, 1] (so ownership cannot be invented)

(take() and dummy() also exist; they only move tickets around.)

Fractional permissions are a proof technique, not a Rust feature. They exist only while Verus checks the program.

The box and its rule

The box holds three things: the key to the real counter, and the box’s own half (call it a stub) of each of the two tickets. As in chapter 24, a constant holds ids and a label names the rule:

#![allow(unused)]
fn main() {
pub struct CountK {
    pub counter_id: int,
    pub a_id: Loc,
    pub b_id: Loc,
}

// V: the contents of the box: the key to the real counter, and the box's half
// (the "stub") of each of the two tickets.
pub struct CountV {
    pub perm: PermissionU32,
    pub stub_a: FracGhost<int>,
    pub stub_b: FracGhost<int>,
}

// The label that names the rule. It holds no data.
pub struct CountInv;

impl InvariantPredicate<CountK, CountV> for CountInv {
    open spec fn inv(k: CountK, v: CountV) -> bool {
        // the key and the stubs belong to the right counter and the right tickets
        &&& v.perm.id() == k.counter_id
        &&& v.stub_a.id() == k.a_id
        &&& v.stub_b.id() == k.b_id
        // each stub is exactly half of its ticket (the other half is out with a thread)
        &&& v.stub_a.frac() == 0.5real
        &&& v.stub_b.frac() == 0.5real
        // a and b are each 0 or 1
        &&& 0 <= v.stub_a@ < 2
        &&& 0 <= v.stub_b@ < 2
        // the counter equals a + b
        &&& v.perm.value() == v.stub_a@ + v.stub_b@
    }
}

type Inv = AtomicInvariant<CountK, CountV, CountInv>;
}

The rule has four parts:

  1. The key and the stubs belong to the right counter and the right tickets (the ids).
  2. Each stub is exactly half of its ticket. The other half is out with a thread.
  3. The numbers a and b are each 0 or 1.
  4. The counter equals a + b. This line connects the tickets to the real counter.

At the start everything is 0, so the rule holds: counter == 0 + 0.

What one thread does

The work of one thread is a function. Its parameters show everything it depends on, and its requires and ensures say what it needs and what it promises:

#![allow(unused)]
fn main() {
// The work of one thread: add 1 to the real counter and, in the same atomic step, move
// its ticket from "not added" (0) to "added" (1).
//
//   ptr     the real atomic counter
//   inv     the shared box that keeps the rule counter == a + b
//   ticket  this thread's half of its ghost number (proof-only)
//   which   0 if this is thread A (ticket for `a`), 1 if thread B (ticket for `b`)
fn add_one(
    ptr: &PAtomicU32,
    Tracked(inv): Tracked<&Inv>,
    Tracked(ticket): Tracked<&mut FracGhost<int>>,
    Ghost(which): Ghost<int>,
)
    requires
        which == 0 || which == 1,
        inv.constant().counter_id == ptr.id(),
        old(ticket).id() == (if which == 0 {
            inv.constant().a_id
        } else {
            inv.constant().b_id
        }),
        old(ticket).frac() == 0.5real,
        old(ticket)@ == 0,  // "I have not added yet"
    ensures
        final(ticket).id() == old(ticket).id(),
        final(ticket).frac() == 0.5real,
        final(ticket)@ == 1,  // "I have added"
{
    open_atomic_invariant!(inv => v => {
        let tracked CountV { mut perm, mut stub_a, mut stub_b } = v;

        // the real increment
        ptr.fetch_add(Tracked(&mut perm), 1);

        proof {
            // the ghost update, in the same step: move my ticket from 0 to 1
            if which == 0 {
                stub_a.combine(ticket.take());  // join the halves: now we own all of `a`
                stub_a.update(1);               // allowed: we own everything. a: 0 -> 1
                *ticket = stub_a.split();       // split again: I keep a half, the box keeps a half
            } else {
                stub_b.combine(ticket.take());
                stub_b.update(1);
                *ticket = stub_b.split();
            }
            v = CountV { perm, stub_a, stub_b };
        }
    });
}
}

Read the contract first.

  • ptr is the real counter. inv is the shared box. ticket is this thread’s half of its ticket, passed as a mutable proof-only reference (Tracked(&mut ...)). which is a proof-only number saying whether this is thread A or thread B.
  • Requires: the ticket belongs to this counter’s box; it is a half; and it says 0, “I have not added yet”.
  • Ensures: the ticket is still the same ticket and still a half; and it now says 1, “I have added”.

Now the body. Inside the box, in one atomic step:

  1. ptr.fetch_add(..., 1) adds 1 to the real counter.
  2. stub_a.combine(ticket.take()) joins the thread’s half with the box’s half. The thread now owns all of a. (take() moves the ticket out of the mutable reference.)
  3. stub_a.update(1) changes a from 0 to 1. This is allowed because the fraction is 1.
  4. *ticket = stub_a.split() splits the number again: the box keeps one half, and the thread gets the other half back, now saying 1.

When the box is closed, the rule must hold: the counter went up by one and a went from 0 to 1, so counter == a + b still holds.

How does step 3 know that a was 0? The thread’s half says 0 (that is the requires), and two halves of the same number always agree. So the box’s half also says 0, and the update makes it 1.

Starting the threads

The parent first builds the tickets and the box:

#![allow(unused)]
fn main() {
    // The two tickets (ghost, proof-only). Each starts at value 0 with ownership 1,
    // then is split in two halves: one for the thread, one for the box.
    let tracked mut stub_a = FracGhost::<int>::new(0);
    let tracked mut stub_b = FracGhost::<int>::new(0);
    let tracked ticket_a = stub_a.split();
    let tracked ticket_b = stub_b.split();
    let ghost a_id = ticket_a.id();
    let ghost b_id = ticket_b.id();

    // The real counter, shared between the threads.
    let (ptr, Tracked(perm)) = PAtomicU32::new(0);
    let ptr = Arc::new(ptr);

    // The shared box. Everything is 0, so the rule counter == a + b holds.
    let tracked inv = Inv::new(
        CountK { counter_id: ptr.id(), a_id: stub_a.id(), b_id: stub_b.id() },
        CountV { perm, stub_a, stub_b },
        0,
    );
    let tracked inv_box = Shared::new(inv);

    // One handle to the box, and one to the counter, for each thread.
    let tracked inv_for_a = inv_box.clone();
    let tracked inv_for_b = inv_box.clone();
    let ptr_for_a = ptr.clone();
    let ptr_for_b = ptr.clone();
}
  • Each ticket starts at 0 with full ownership, and is split into a half for the thread and a half for the box.
  • The box is shared with Shared, vstd’s duplicable proof-only container. Each thread gets a clone, and borrow() gives a reference to the box. (This plays the role that Arc<Tracked<...>> played in chapter 24.)

Each thread moves its ticket into a closure, runs add_one, and returns the ticket:

#![allow(unused)]
fn main() {
    let thread_a = vstd::thread::spawn(
        move || -> (r: Tracked<FracGhost<int>>)
            ensures
                r@.id() == a_id,
                r@.frac() == 0.5real,
                r@@ == 1,
            {
                let tracked mut ticket = ticket_a;
                add_one(&ptr_for_a, Tracked(inv_for_a.borrow()), Tracked(&mut ticket), Ghost(0));
                Tracked(ticket)
            },
    );
}

The closure’s ensures is the road back (chapter 23): it promises that the returned ticket is the right one and says 1.

The parent’s conclusion

#![allow(unused)]
fn main() {
    // The parent joins both threads and gets both tickets back, both saying "added".
    if let (Ok(join_a), Ok(join_b)) = (thread_a.join(), thread_b.join()) {
        let Tracked(ticket_a) = join_a;
        let Tracked(ticket_b) = join_b;
        let n: u32;
        open_atomic_invariant!(inv_box.borrow() => v => {
            let tracked CountV { perm, stub_a, stub_b } = v;
            n = ptr.load(Tracked(&perm));
            proof {
                // the box's halves agree with the tickets we hold: a == 1 and b == 1
                stub_a.agree(&ticket_a);
                stub_b.agree(&ticket_b);
                v = CountV { perm, stub_a, stub_b };
            }
        });
        // the rule says counter == a + b == 1 + 1
        assert(n == 2);
    }
}

After the joins the parent holds both tickets. Inside the box, agree shows that the box’s halves say the same as the parent’s halves, so a == 1 and b == 1. The rule gives counter == a + b == 2.

Notice that nobody ever owned the real counter exclusively. The counter stayed shared the whole time. What the parent used was the tickets and the rule that connects them to the counter.

A thread that does not cooperate

Suppose a third thread adds 1 to the counter without having a ticket. To touch the counter it must open the box and take the key. When it puts the key back, it must show counter == a + b. It cannot change a or b, because that needs all the ownership of a ticket, and it has none. So the rule fails and Verus rejects the thread.

This is the safety net of the whole scheme: the key to the counter lives inside the box, so everyone who touches the counter must go through the rule.

Why the rule needs 0 <= a < 2

The bound lines may look like decoration. They are not. Delete the two lines 0 <= v.stub_a@ < 2 and 0 <= v.stub_b@ < 2 and Verus reports:

error: precondition not satisfied
   --> count_to_2.rs:101:9
    |
101 |         ptr.fetch_add(Tracked(&mut perm), 1);
    |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    |
   --> vstd/atomic.rs:317:16
    |
    = note: failed precondition

fetch_add has a precondition: adding must not overflow the counter’s type. From counter == a + b alone, Verus cannot rule out that the sum is huge. The two bounds give counter <= 2, so there is no overflow. When a proof fails like this, read the failed precondition, ask what fact it needs, and add it to the rule.

A word about resource algebras

Fractional tickets are one example of a general technique called resource algebras (also called PCMs, partial commutative monoids): proof-only values that can be combined, with rules about which combinations are valid and how a value may be updated. vstd has the general framework (ResourceAlgebra, PCM) and several ready-made ones: fractions, maps (GhostMap), a single variable with an owner (GhostVar), and others. You do not need the general theory to use them. The rule of thumb: when a fact is about history, record the history in a ghost resource and tie it to the real state with an invariant.

What is and is not proved

  • After both threads finish and the parent joins them, the counter equals 2.
  • This holds for every interleaving of the two threads.
  • It does not say anything if a join fails (the parent only reaches the assertion when both joins succeed).
  • It holds for exactly these two threads. Adding a third adder means adding a third ticket and a third term to the rule.
