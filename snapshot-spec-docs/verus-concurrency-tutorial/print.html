Threads that share nothing

This chapter starts concurrency in the easiest possible place: different threads work on different data, and nothing is shared between them. This kind of data parallelism is easy to reason about and holds no surprises. The Verus specifications and proofs here are not much different from those in earlier chapters.

Background: how basic threads work in Rust

In Rust, spawn(closure) starts a new thread that runs the closure and returns a JoinHandle. handle.join() waits for the thread to finish and returns the closure’s result.

When a program needs several threads to work on different data, it simply moves each piece of data into the thread that will use it. That thread becomes the sole owner of the data. The Rust compiler guarantees that no other thread can read or write it, so we can reason about the data inside the thread as if there were no concurrency.

What vstd::thread::spawn adds

vstd provides vstd::thread::spawn and vstd::thread::JoinHandle, wrappers around the std ones. The thread itself is the same; what differs is the contract Verus sees:

  • The closure passed to spawn can carry requires and ensures, like any function; see Closures in the chapter on higher-order functions. Nothing about this is special to threads, except where the ensures ends up.
  • At the call to spawn, Verus checks that the closure’s requires holds.
  • The closure’s ensures becomes a fact about the JoinHandle. Verus checks that the closure satisfies it, just as in sequential code.
  • When the parent calls join, the only thing Verus lets it know about the thread’s work is what the closure’s ensures says. To tell the parent anything useful, the thread must promise it in an ensures clause. This will matter again in every later chapter.
  • join returns Result<T, ()>, not std’s Result<T, Box<dyn Any>>. It is Err if the thread panicked, and then the parent learns nothing.

An example

Suppose we want to compute a tight window for a list of numbers: a pair [lo, hi] where lo is the smallest number in the list and hi is the largest. We cut the list into two halves, let two threads each work on one half, and have the parent combine their results.

The complete program is in my_threads_min_max.rs. Below are the parts that matter for threads.

The specification

#![allow(unused)]
fn main() {
pub open spec fn tight(v: Seq<u64>, lo: u64, hi: u64) -> bool {
    &&& forall|i: int| 0 <= i < v.len() ==> lo <= #[trigger] v[i] && v[i] <= hi
    &&& exists|i: int| 0 <= i < v.len() && v[i] == lo
    &&& exists|i: int| 0 <= i < v.len() && v[i] == hi
}
}

The work of one thread

scan walks over one piece and returns the tight window of that piece. We skip the implementation of scan here and show only its signature and contract.

#![allow(unused)]
fn main() {
fn scan(v: &Vec<u64>) -> (out: (u64, u64))
    requires
        v.len() > 0,
    ensures
        tight(v@, out.0, out.1),
}

The parent

scan_with_two_threads splits the list, starts one thread per half, and combines the two answers.

#![allow(unused)]
fn main() {
fn scan_with_two_threads(v: &Vec<u64>) -> (out: Result<(u64, u64), ()>)
    requires
        v.len() >= 2,
    ensures
        out is Ok ==> tight(v@, out.unwrap().0, out.unwrap().1),
{
    let mid = v.len() / 2;
    let mut left = v.clone();
    let right = left.split_off(mid);

    /*Two threads each scan half of the vectors*/
    let handle_left = spawn(
        move || -> (r: (u64, u64))
            ensures
                tight(v@.subrange(0, mid as int), r.0, r.1),
            { scan(&left) },
    );
    let handle_right = spawn(
        move || -> (r: (u64, u64))
            ensures
                tight(v@.subrange(mid as int, v@.len() as int), r.0, r.1),
            { scan(&right) },
    );

    if let (Ok(l), Ok(r)) = (handle_left.join(), handle_right.join()) {
        let lo = if l.0 < r.0 { l.0 } else { r.0 };
        let hi = if l.1 > r.1 { l.1 } else { r.1 };
        proof {
            let left_seq = v@.subrange(0, mid as int);
            let right_seq = v@.subrange(mid as int, v@.len() as int);
            assert forall|i: int| 0 <= i < v@.len() implies lo <= #[trigger] v@[i]
                && v@[i] <= hi by {
                if i < left_seq.len() {
                    assert(v@[i] == left_seq[i]);
                } else {
                    assert(v@[i] == right_seq[i - left_seq.len()]);
                }
            }
        }
        Ok((lo, hi))
    } else {
        Err(())
    }
}
}
  1. Splitting. The parent borrows the list, makes a copy with clone, and cuts the copy in two with split_off. Each half is a Vec of its own, so each can move into one closure.
  2. Starting the threads. Each closure scans its own half. Its ensures says “the window I return is the tight window of my half”.
  3. The proof block near the end of scan_with_two_threads. It is a case split on which half an index falls in. It lets Verus use what each thread promised about its own half.
  4. The error case. If a thread panics, join returns Err, and the function returns Err without claiming anything.

What if the thread promises nothing?

Delete the two ensures clauses from the closures and Verus no longer accepts the parent’s postcondition. This is the error:

error: postcondition not satisfied
   |
63 |         out is Ok ==> tight(v@, out.unwrap().0, out.unwrap().1),
   |         ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ failed this postcondition
...
error: assertion failed
85 |             assert forall|i: int| 0 <= i < v@.len() implies lo <= #[trigger] v@[i]

After join, the parent knows nothing about what l and r contain, so it cannot prove that the combined window is tight. The facts have to travel through the ensures.

What comes next

The threads here never touched the same data. In the next few chapters we will discuss how to reason about more complicated code in which multiple threads update shared data concurrently.

Atomic invariants

In the last chapter every thread had its own data. Unfortunately, in many concurrent Rust projects, threads do write to the same data concurrently. That is what makes concurrency hard to verify.

Verus offers more than one way to reason about concurrency. (The VerusSync framework, with its tokenized state machines, has its own tutorial and reference book.) The next few chapters present one set of tools, based on the approach of the Iris separation logic (Jung et al., POPL 2015). It reasons with two ingredients: an invariant, which says which states of the shared data are allowed, and a protocol, which says how one valid state may change into another and which thread may take which step. This chapter covers invariants, in the form of atomic invariants. Chapter 25 covers protocols, built with ghost resources.

This chapter has two sections. The first shows how to reason about atomic variables, where atomic invariants must be defined explicitly. The second shows how to reason about lock-protected data, where part of the atomic invariant is embedded inside the lock.

Background: how threads share and change data in Rust

Rust normally allows many readers or one writer, never both at once. Sharing a value between threads means putting it in an Arc (an atomically reference-counted pointer). But an Arc shares ownership, not the right to change the value: through an Arc you only get a shared reference, which is read-only. (If the threads only read the value, an Arc alone is enough.)

To change a shared value, the value’s type must have interior mutability, which means it can be changed through a shared reference. Rust offers three kinds:

  • an atomic type such as AtomicU64: each operation is one indivisible hardware step;
  • a lock (Mutex, RwLock): one thread at a time may change the data (section 24.2);
  • Cell and RefCell: not safe across threads.

Section 24.1 uses atomics, which Verus wraps in types such as PAtomicU64. Section 24.2 uses a lock, namely vstd’s RwLock.

Why atomic invariants?

With one owner, Verus knows the value of a variable by following ownership: a &mut reference means nobody else can change it, so the value before and after a call can be written in a specification.

A shared atomic is different. Say several threads share an atomic counter and can update it at any moment. It is very difficult to say exactly what the value of the counter is, because it can change at any time. The same issue applies to lock-protected data: once the lock is released, the code cannot know for sure what the value of the shared data is.

Of course, not knowing exactly what the value is does not mean that we cannot reason about its properties. If every thread only increases an atomic counter or a lock-protected counter, we can safely conclude that the counter’s value is at least its initial value (ignoring overflow). If every thread only adds 2 to a counter whose initial value is 0, we can safely conclude that the counter’s value is always even (ignoring overflow). Such a statement is called an invariant.

An invariant says which states of the shared data are allowed. It does not say when one valid state may change into which other valid state, or which thread may make such a transition. That is the job of a protocol, which chapter 25 covers.

Using atomic invariants in Verus

In Verus, we can associate an atomic invariant with shared data. Verus models two things in every atomic invariant.

  • The permission is a proof-only object for the variable. You cannot touch the real variable without holding its permission; there is only one permission, and it cannot be copied. For lock-protected data in Rust, the lock itself acts like a permission. Atomic variables in Rust have no permission, so Verus needs some extra mechanism to associate one with each atomic variable. This makes it feasible to verify that every update follows the invariant.

  • The invariant is a rule saying which states of the shared data are allowed. It holds in the stable states, but not necessarily in the middle of an atomic step or a lock critical section.

To change a shared variable, a thread has to open the atomic invariant, take the permission out, change the variable in an atomic step (or in one lock section), and put the permission back. As soon as the atomic invariant is opened, Verus knows that the variable satisfies the rule written in it; right before it is closed, Verus needs to prove that the variable still satisfies that rule.

Because the permission is only ever out of the atomic invariant for one (logically) atomic step, and one atomic step cannot be interrupted, no other thread ever sees a half-finished change.

Two ways to use atomic invariants

  • With an atomic variable, a thread borrows the permission for one atomic step (section 24.1).
  • With a lock, a thread keeps the permission for as long as it holds the lock, which can be many steps (section 24.2).

Atomic Invariants for Atomic Variables

This section applies the idea of atomic invariants to Rust’s atomic variables. We explain how to create a permission for an atomic variable, how to define the invariant rule, and how to open and close the atomic invariant.

The atomic variable and its permission

A challenge in applying atomic invariants to atomic variables is that, in Rust, atomic variables are not associated with permissions: any thread that receives a clone of an Arc holding an atomic variable can update it at any time. Therefore, vstd provides a wrapper for every Rust atomic type that introduces permissions. In the rest of this section we use PAtomicU64, the vstd wrapper for the Rust type AtomicU64, in our examples. The details of these wrapper types can be found in vstd/atomic.rs.

PAtomicU64 is a wrapper around AtomicU64. All the APIs of AtomicU64, such as load, store, fetch_add, compare_exchange, and many others, also exist for PAtomicU64. The main difference is that AtomicU64::new(..) returns one value, the atomic variable of type AtomicU64, while PAtomicU64::new(..) returns two: the atomic variable, of type PAtomicU64, and the permission associated with it, of type PermissionU64, as shown below.

#![allow(unused)]
fn main() {
  let (x, Tracked(mut perm)) = PAtomicU64::new(0);
}

There are two useful properties relating the atomic variable x and its corresponding permission perm:

  • perm.id() equals x.id(): each of them has an integer id, and the ids are used to match them with each other. In addition, all the APIs that read or write the atomic data take an extra ghost parameter in PAtomicU64: the permission. They have a precondition saying that the permission passed in must be the permission of this very atomic variable.
  • perm.value() always matches the u64 value stored inside x. This relationship is maintained automatically by the PAtomicU64 APIs, and it is crucial for our verification. In fact, atomic invariants describe properties held by the tracked ghost variable perm, not directly by x.

Here is an example that creates a PAtomicU64 counter whose initial value is 0 and then uses its permission to update the value to 11.

#![allow(unused)]
fn main() {
fn permission_demo() {
    let (x, Tracked(mut perm)) = PAtomicU64::new(0);
    x.store(Tracked(&mut perm), 11);
    let v = x.load(Tracked(&perm));
    assert(v == 11);
}
}

Here one function owns the permission, so nothing else is needed. With several threads the permission has to be shared, which is what the rest of this section is about.

The rule: InvariantPredicate

vstd provides a trait InvariantPredicate<K, V> to specify the invariant rule. This trait is useful not only for AtomicInvariant, but also for LocalInvariant (an invariant that is not shared between threads; see vstd/invariant.rs), for the RwLock that section 24.2 introduces (see vstd/rwlock.rs), and for the atomic_ghost types (see vstd/atomic_ghost.rs).

#![allow(unused)]
fn main() {
pub trait InvariantPredicate<K, V> {
    spec fn inv(k: K, v: V) -> bool;
}
}

In general, k is an (optional) constant that helps define the invariant rule, and v is the variable that is supposed to satisfy the invariant.

In the code below, EvenInv describes an invariant that a permission perm must satisfy: perm must correspond to a specific atomic variable (perm.id() == x_id), and the value associated with the permission must be an even number (perm.value() % 2 == 0).

#![allow(unused)]
fn main() {
pub struct EvenInv;

impl InvariantPredicate<int, PermissionU64> for EvenInv {
    open spec fn inv(x_id: int, perm: PermissionU64) -> bool {
        &&& perm.id() == x_id  // the permission belongs to our atomic variable
        &&& perm.value() % 2 == 0  // the property we care about
    }
}
}

The AtomicInvariant type

Now we can look at the atomic invariant type in Verus.

AtomicInvariant<K, V, Pred> is a proof-only generic type. An object of this type holds a constant of type K and a variable of type V. The type Pred, which implements InvariantPredicate<K, V>, supplies the rule inv that every state of the variable must satisfy.

In the example here, we define an AtomicInvariant type Inv. An Inv object will hold a permission of type PermissionU64, and the permission has to satisfy the rule specified by EvenInv: the permission corresponds to a specific atomic variable identified by an x_id of type int (i.e., type K is int), and the value of the permission is always even.

#![allow(unused)]
fn main() {
    type Inv = AtomicInvariant<int, PermissionU64, EvenInv>;

    ...

    let (x, Tracked(perm)) = PAtomicU64::new(0);
    let tracked inv = Inv::new(x.id(), perm, 1);
    let x = Arc::new(x);
    let inv = Arc::new(Tracked(inv));
}

Note that the code above also shows how a parent thread prepares the atomic variable x and the atomic invariant inv, both wrapped in Arcs so that they can be shared. Later on, every thread can get a clone of x and a clone of inv, which contains the permission to update x.

  • x.id() is the variable’s id, which is used to match its corresponding permission.
  • Inv::new(x.id(), perm, 1) creates the atomic invariant. It takes the constant (the id), the contents (the permission), and a number called the namespace, which you can ignore for now.

Creating the atomic invariant checks that inv holds for the starting contents: the value 0 is even, and x.id() matches perm.id().

Atomic updates to an atomic variable using a permission

As we have seen, if a thread wants to update an atomic variable x: PAtomicU64, it has to obtain the corresponding permission, which is owned by an atomic invariant inv.

Verus provides a macro open_atomic_invariant! to open an atomic invariant, take the permission out, perform one atomic update, and put the permission back: open_atomic_invariant!(invariant => permission => {/*atomic update that uses the permission*/});. Right before the atomic update, we can assume that the invariant rule holds; at the end of the update, Verus needs to prove that the rule still holds.

Here is an example of atomically adding 2 to an atomic counter; its complete program is in my_atomic_counter_fetch_add.rs:

#![allow(unused)]
fn main() {
// One physical step (fetch_add), so one open/close of the invariant.
pub fn add_two(x: &PAtomicU64, Tracked(inv): Tracked<&Inv>)
    requires
        inv.constant() == x.id(),
{
    open_atomic_invariant!(inv => perm => {
        x.fetch_add_wrapping(Tracked(&mut perm), 2);
    });
}
}
  • The requires line says that the invariant passed into add_two has to be the one for the atomic variable x.
  • open_atomic_invariant!(inv => perm => { ... }) takes the permission perm out of the atomic invariant inv. At the closing brace the permission goes back into the invariant, and Verus checks that the invariant rule still holds.
  • Only one atomic operation is allowed between the braces.

Where is the proof? None is needed here. At the closing brace Verus must show that the new value is even. It knows two things: the old value was even (the rule, assumed when inv was opened), and the instruction added 2. Adding 2 to an even number gives an even number, and Verus’s solver sees that on its own.

Here is another atomic operation, which also uses the permission from the atomic invariant temporarily:

#![allow(unused)]
fn main() {
// One physical step (store), so one open/close of the invariant.
pub fn reset(x: &PAtomicU64, Tracked(inv): Tracked<&Inv>)
    requires
        inv.constant() == x.id(),
{
    open_atomic_invariant!(inv => perm => {
        x.store(Tracked(&mut perm), 0);
    });
}
}

Sharing the variable and the atomic invariant between threads

As we mentioned briefly above, to give every thread access to the variable and the atomic invariant, each goes into an Arc, and every thread gets its own clone of both.

#![allow(unused)]
fn main() {
fn spawn_adder(x: &Arc<PAtomicU64>, inv: &Arc<Tracked<Inv>>) -> (h: JoinHandle<()>)
    requires
        inv@.constant() == x.id(),
{
    let (x, inv) = (x.clone(), inv.clone());
    spawn(move || -> (r: ()) { add_two(&x, Tracked(inv.borrow())) })
}
}

Now we can tie everything together in the run_threads function below. It creates the counter and the atomic invariant, shares both with four threads (two that add 2 and two that reset to 0), waits for all of them, and then reads the counter by opening the atomic invariant once more:

#![allow(unused)]
fn main() {
fn run_threads() -> (out: Result<u64, ()>)
    ensures
        out is Ok ==> out.unwrap() % 2 == 0,
{
    let (x, Tracked(perm)) = PAtomicU64::new(0);
    let tracked inv = Inv::new(x.id(), perm, 1);
    let x = Arc::new(x);
    let inv = Arc::new(Tracked(inv));

    let a0 = spawn_adder(&x, &inv);
    let a1 = spawn_adder(&x, &inv);

    let r0 = spawn_resetter(&x, &inv);
    let r1 = spawn_resetter(&x, &inv);

    let ok = a0.join().is_ok() && a1.join().is_ok() && r0.join().is_ok() && r1.join().is_ok();

    if ok {
        let result;
        open_atomic_invariant!(inv.borrow() => perm => {
            result = x.load(Tracked(&perm));
        });
        Ok(result)
    } else {
        Err(())
    }
}
}

Its ensures clause promises out.unwrap() % 2 == 0. It can promise this because x.load returns a value that has to satisfy the EvenInv rule.

When the rule is broken

Change the operation to add 1 instead of 2. Verus rejects the program:

error: Cannot show invariant holds at end of block
   |
   | /     open_atomic_invariant!(inv => perm => {
   | |         x.fetch_add_wrapping(Tracked(&mut perm), 1);
   | |     });
   | |______^

Atomic invariants about two variables

An atomic invariant can be used to describe properties held by multiple shared variables together.

To see this, we look at another example: the tight window [lo, hi] of chapter 23, now with much more parallelism. Imagine that many threads are processing numbers and updating the two shared variables lo and hi concurrently. We want to prove that lo <= hi always holds, whatever order the threads run in. The complete program is in my_atomic_two_vars.rs.

As in the even-counter example above, we create lo and hi as PAtomicU64 instead of AtomicU64, so each is associated with a permission. Unlike the earlier example, the InvariantPredicate and the AtomicInvariant now have to account for two PAtomicU64 variables and two permissions.

So we define the K type to include two constant ids and the V type to include two permissions. This allows the inv function to express the relationship between the two variables: v.lo_p.value() <= v.hi_p.value().

#![allow(unused)]
fn main() {
pub struct K {
    pub lo_id: int,
    pub hi_id: int,
}

pub struct V {
    pub lo_p: PermissionU64,
    pub hi_p: PermissionU64,
}

// A permission is linear: each one lives in exactly one invariant, so we cannot also
// give `lo` or `hi` its own separate invariant. Properties of a single variable
// (e.g. `lo <= 100`) are simply extra clauses in this joint predicate.
pub struct WindowInv;

impl InvariantPredicate<K, V> for WindowInv {
    open spec fn inv(k: K, v: V) -> bool {
        &&& v.lo_p.id() == k.lo_id
        &&& v.hi_p.id() == k.hi_id
        &&& v.lo_p.value() <= v.hi_p.value()  // the relation between the two variables
    }
}

type Inv = AtomicInvariant<K, V, WindowInv>;
}

This two-variable invariant is used in the same way as the one-variable invariant. Whether a thread updates both variables or just one of them (e.g., only lo in widen_down and only hi in widen_up), it needs to open the invariant to get the permission or permissions.

#![allow(unused)]
fn main() {
// One physical step (fetch_min on lo), so one open/close of the invariant.
pub fn widen_down(lo: &PAtomicU64, Tracked(inv): Tracked<&Inv>, n: u64)
    requires
        inv.constant().lo_id == lo.id(),
{
    open_atomic_invariant!(inv => v => {
        lo.fetch_min(Tracked(&mut v.lo_p), n);
    });
}
}

widen_up is the same, with fetch_max on hi. Both fetch_min and fetch_max are atomic APIs that update the atomic variable in one atomic step. They make sure that the new value of the atomic variable is the smaller (for fetch_min) or the larger (for fetch_max) of the original value and the parameter. Each operation opens the same shared atomic invariant. Its contents v hold both permissions, and the operation uses just one of them (v.lo_p here). When the block closes, Verus checks the rule lo <= hi.

An operation that does both, widening the window to contain v, is just the two steps in order:

#![allow(unused)]
fn main() {
pub fn widen(lo: &PAtomicU64, hi: &PAtomicU64, Tracked(inv): Tracked<&Inv>, v: u64)
    requires
        inv.constant().lo_id == lo.id(),
        inv.constant().hi_id == hi.id(),
{
    widen_down(lo, Tracked(inv), v);
    widen_up(hi, Tracked(inv), v);
}
}

This widen function performs two atomic steps. At most one of them changes anything (if v is below lo, it is also below hi), so from the outside it looks like one step. Since we only need to prove lo <= hi and each atomic step preserves it, we do not need to reason about which step changes a shared variable.

Reading both variables

With two variables there is one thing you cannot do: read both in a single atomic step. No atomic instruction reads two variables at once, so a program that loads lo and then loads hi cannot claim anything about the pair: another thread may have changed one of them in between. (Of course, once all threads have finished updating, reading both would be fine. But to let Verus know that all the threads are done, we need a proof tool such as FracGhost, a kind of PCM, which chapter 25 introduces.) What we can prove here is a claim in proof mode, as a fact about the two permissions, by opening the atomic invariant inside a proof block:

#![allow(unused)]
fn main() {
    // Exec code cannot read two atomics in one atomic step, so the relation is stated
    // about the ghost permissions, in proof mode, by opening the invariant there.
    let Tracked(credit) = vstd::invariant::create_open_invariant_credit();
    proof {
        open_atomic_invariant_in_proof!(credit => inv.borrow() => v => {
            assert(v.lo_p.value() <= v.hi_p.value());
        });
    }
}

This statement is true, but weaker than in the single-variable case: it is about the proof-only permissions, not about two numbers the program holds. Section 24.2 shows how a lock gives you a statement about real values.

Small notes

  • Namespaces. The number given to Inv::new (the 1 above) is a namespace. Verus uses it to forbid opening an atomic invariant while it is already open, which would let one thread hold the permission twice. It only matters when atomic invariants nest, so you can pick any number for now.
  • Why Arc<Tracked<Inv>>. Threads need to own what they share, so the atomic invariant goes in an Arc like the variable. In chapter 25 we will use Shared, vstd’s tracked equivalent.

Atomic Invariants for Lock-Protected Data

The previous section explained how to use atomic invariants to reason about concurrent updates to atomic variables. However, an atomic variable holds only one machine word, and an atomic instruction changes only one variable at a time, so Rust threads need other means, such as locks, to share larger data with each other.

This section explains how to use the idea of atomic invariants to reason about lock-protected data. We use the same running example as before, the tight window [lo, hi] with the rule lo <= hi. The complete program is in my_rwlock_window.rs.

Rust locks and their inherent permissions

In Rust, a lock that protects data of type V is written RwLock<V>, Mutex<V>, and so on. Conceptually, a lock is very much like a permission: lock-protected data can only be accessed when the corresponding lock is held. To avoid bugs, it is often helpful to think about which properties the lock-protected data maintains at the boundaries of lock critical sections. Those properties may be violated in the middle of a critical section (i.e., after the lock is acquired and before it is released), but they must be restored right before the lock is released.

Here is how one uses Rust’s std::sync::RwLock to implement the widen_down operation from the previous section. Note that lo and hi are no longer two separate atomic variables: they are now protected by the same lock.

#![allow(unused)]
fn main() {
struct Window {
    lo: u64,
    hi: u64,
}

...

fn widen_down(lock: &RwLock<Window>, n: u64) {
    let mut w = lock.write().unwrap(); // guard: blocks until we hold the lock
    if n < w.lo {
        w.lo = n;
    }
} // the guard is dropped here, and that releases the lock automatically
}

The lock in vstd that embodies atomic invariants

Verus’s read-write lock has the type vstd::rwlock::RwLock<V, Pred>. It is similar to Rust’s std::sync::RwLock<V> in that it owns shared data of type V, which cannot be accessed unless the lock is acquired. It differs in that it also owns a rule, given by Pred. This rule defines a property of the shared data that holds when the lock has just been acquired and must hold again when the lock is released.

The code below defines a RwLockPredicate named LoLeHi whose rule says that the lo field should be less than or equal to the hi field of the Window object. LoLeHi then helps define a vstd read-write lock type Lock that owns a shared Window object and enforces the LoLeHi rule on that object.

#![allow(unused)]
fn main() {
pub struct Window {
    pub lo: u64,
    pub hi: u64,
}

pub struct LoLeHi;

impl RwLockPredicate<Window> for LoLeHi {
    open spec fn inv(self, w: Window) -> bool {
        w.lo <= w.hi
    }
}

type Lock = RwLock<Window, LoLeHi>;
}

As we can see, vstd::rwlock::RwLock hides the complexity of permissions, atomic invariants, and so on, so that we can use it in a way very similar to Rust’s locks. Readers who are interested in the implementation can refer to vstd/rwlock.rs.

Updating data protected by vstd::rwlock::RwLock

It is very easy to rewrite the widen_down function to use vstd::rwlock::RwLock, as follows:

#![allow(unused)]
fn main() {
pub fn widen_down(lock: &Lock, n: u64) {
    let (mut w, handle) = lock.acquire_write(); // blocks until we hold the lock
    if n < w.lo {
        w.lo = n;
    }
    handle.release_write(w); // unlike std's lock, the release is an explicit call
}
}

Verus will verify that the property w.lo <= w.hi holds right before the lock is released.

Lock operations that atomics cannot do

In the previous section, the widen function needs two atomic instructions, lo.fetch_min and then hi.fetch_max, and Verus has to prove that the invariant holds right after each of them. With a lock, widen can be done in a single critical section, as follows, and Verus only needs to prove that the invariant holds once, at the end of the critical section.

#![allow(unused)]
fn main() {
pub fn widen(lock: &Lock, n: u64) {
    let (mut w, handle) = lock.acquire_write();
    if n < w.lo {
        w.lo = n; //widen down
    } else if n > w.hi {
        w.hi = n; //widen up
    }
    handle.release_write(w);
}
}

Of course, in this case the invariant holds with atomic variables and with locks alike. However, there are cases where the invariant cannot be proved when the implementation uses atomic variables.

Imagine an operation that replaces the window with a new [a, b], where a <= b. The implementation with a lock is straightforward:

#![allow(unused)]
fn main() {
// Replace the window with [a, b].
pub fn reset_to(lock: &Lock, a: u64, b: u64)
    requires
        a <= b,
{
    let (mut w, handle) = lock.acquire_write();
    w.lo = a;
    // lo <= hi is BROKEN here if a > the old hi (e.g. [20, 30] -> lo = 50 gives [50, 30]).
    // Under the lock nobody else can see this state, so it is fine.
    w.hi = b;
    // lo = a <= b = hi: the invariant holds again, and release_write checks exactly that.
    handle.release_write(w);
}
}

Unfortunately, it is not possible to implement this operation correctly with two separate atomic variables and plain writes. Imagine that the old window was [20, 30] and the new window [a, b] is [50, 60]. The invariant lo <= hi is broken when we update lo to a: the window temporarily becomes [50, 30]. With a lock, this is not a problem, because no other thread can see this temporary state, so the invariant only needs to be re-established right before the lock is released. With atomic variables, the invariant would be violated at that moment, and the code would be buggy, because other threads could update lo or hi while the window has the invalid value [50, 30].

Sharing the lock-protected variable between threads

Threads share the lock through an Arc; at any time, the parent thread or one of the child threads can read both Window fields inside a lock critical section:

#![allow(unused)]
fn main() {
fn run_threads() -> (out: (u64, u64))
    ensures
        out.0 <= out.1,
{
    ...

    // Both fields are read in one critical section, so they are consistent.
    let handle = lock.acquire_read();
    let w = handle.borrow();
    let result = (w.lo, w.hi);
    handle.release_read();
    result
}
}

The function run_threads promises out.0 <= out.1, and this time the promise is about two numbers that the program really holds, unlike in the previous section.

When the rule is broken

Remove the line w.hi = b; from reset_to. Now the data is left as [a, old_hi], which may break the rule. Verus rejects the program at the release:

error: precondition not satisfied
   |
   |     handle.release_write(w);
   |     ^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: failed precondition

The failed precondition is release_write’s requires: the rule must hold for the data being put back. Everything before that line was allowed.

What is and is not proved

  • Verus does not check that you release the lock. A handle is not released when it is dropped, and a forgotten release_write would hang the program. So this proves the rule, not the absence of deadlock.
  • vstd::rwlock::RwLock waits by spinning, which is simple but can be slow when many threads compete.
  • vstd has no specification for std::sync::Mutex. The vstd lock is a replacement, not a wrapper, so verifying code that already uses std locks means either switching to the vstd lock or writing a trusted specification yourself.

Coordinating threads with ghost resources

In the previous section, an atomic invariant kept a property true in every stable state of a shared variable (i.e., excluding temporary states in the middle of a lock section). However, sometimes we need to reason not only about which states are valid, but also about what exactly the state is and how it evolves from one valid state to another. In the literature, for example in the Iris separation logic (Jung et al., POPL 2015), this further reasoning requires Partial Commutative Monoids (PCMs) that describe protocols on ghost resources.

Fully understanding PCMs and ghost resources goes beyond this tutorial. Here, we give readers a taste of a simple Verus ghost resource type, FracGhost, and build up to a small example: two threads each add 1 to a shared counter that starts at 0, and after both have finished, we want to prove that the counter is exactly 2.

What is FracGhost<T>?

We have seen a few different sharing modes across threads in the last few chapters:

  • Read share. Ordinary Rust data types can be shared across threads only for reading. If the writable ownership is passed to one thread, no other thread can access the variable;
  • Write share. Special Rust data types, like atomic variables and lock-protected data, can be shared across many threads for writing. But there is no read-only version of this sharing: a thread that is given an atomic variable can both load and store, and a thread that is given an RwLock can choose between acquire_read and acquire_write. To let a thread read, we have to give it the ability to write as well;
  • Write share with invariants. Verus’s PAtomic variables and vstd::rwlock::RwLock do not create a new sharing mode. Once a thread is given an atomic invariant or a RwLock, it can update the corresponding data.

These existing sharing schemes are either too restrictive (e.g., read share) or too difficult to reason about. With write share, no thread knows the exact value of the shared data once it releases the lock or closes the atomic invariant. Similarly, the caller that spawns and then joins all the child threads has no idea about the final value of the shared data, except that the value satisfies the invariant.

FracGhost provides a more flexible and more precise way to share ghost data. As with PAtomic and RwLock data, a thread needs a permission to access the ghost data inside a FracGhost. What is unique is that this permission can be split into fractional permissions and shared across threads: only a full permission (frac() == 1) allows a thread to update the ghost data, while a fractional permission only allows reading. Permissions can be split and merged at any time.

Specifically, a t: FracGhost<T> is a proof-only variable. It contains:

  • t.id(): an id. Fractional permissions split from the same ghost resource have the same id;
  • t@, of type T: the value of the ghost data itself;
  • t.frac(): a fraction of ownership / permission, more than 0 and at most 1.

Here is a small example, all of it proof code:

#![allow(unused)]
fn main() {
proof fn frac_ghost_demo() {
    let tracked mut x = FracGhost::new(100int);
    let tracked y = x.split();
    assert(x.frac() == 0.5real);
    assert(y.frac() == 0.5real);
    assert(x@ == 100);
    assert(y@ == 100);
    x.combine(y);
    assert(x.frac() == 1.0real);
    x.update(200);
    assert(x@ == 200);
}
}

When x is just created, it contains the integer value 100 and holds the full permission to that data. The split cuts the permission into two halves: one is kept by x, and the other is given to a new ghost variable y, which shares its id with x. The first four assert statements show that x and y each hold a fraction of 0.5 and both see the value 100. combine puts them back together, and only then, with the combined full permission, can update change the value.

Fractions of the same ghost value can never add up to more than 1. Together with the rule above, this means that at any moment a thread can look at x.frac() to see the sharing status. In particular, when thread A sees x.frac() == 1, A knows that it is the only holder of x, so it can safely claim any details about x in the postcondition of its closure. The code that eventually joins A can trust those claims, because A was the only writer of x.

Before we conclude that FracGhost solves all concurrency problems, note that FracGhost<T> can only represent ghost data. Therefore, we often need a way to connect the value of a fractional ghost variable with a Rust executable variable, because ultimately we want to prove properties of Rust variables. This connection can be made through an AtomicInvariant, as we will see in the example below.

Example: Count to Two

(We took this example from Chris Hawblitzel’s Formal Methods Summer School. His slides explain it in the section on concurrent count-to-2, and his code is a one-file version.)

Two threads, thread A and thread B, each add 1 to a shared counter that starts at 0. After both have finished, the parent wants to prove that the counter is exactly 2.

Why not an atomic invariant. An invariant holds in every state of the shared data, including the starting state, where the counter is 0. So no invariant over the counter can say “the counter is 2”. In this case, the parent thread needs to know exactly what each thread has done to the counter by the time it joins both threads.

Why not the thread’s postcondition. In chapter 23, a fact travels from a thread to its parent through the closure’s postcondition. But a postcondition can only describe what the thread fully owns. Here the counter is shared, and the only permission for it lives in the atomic invariant, so a thread cannot say “I added 1 to the counter” in its postcondition. It can, however, describe a ghost value that it owns. That leads to the next point.

Using fractional ghost resources

With these challenges in mind, a natural thought is to give each thread (A and B) a FracGhost<int> variable, say inc_a and inc_b, to describe how much each thread has added to the counter. We can leverage fractional permissions to make sure that each thread can describe, in its postcondition, what its increment has been. We can then design an atomic invariant so that the parent thread can figure out the value of the counter from the values of the two increments inc_a and inc_b.

There are two parts to designing an atomic invariant: the rule to enforce and the permissions to hold.

The invariant rule is straightforward: the value of the atomic counter (the Rust variable) should equal the sum of the two threads’ increments, inc_a and inc_b (the ghost resources).

The permissions are the tricky part. Following the examples in the previous chapter, we should put the full permission to access the atomic counter here. Then, since the invariant rule depends on the values of inc_a and inc_b, their permissions need to be stored in the atomic invariant as well. However, as discussed above, we want to make sure that thread A cannot update inc_b and thread B cannot update inc_a, so ordinary full permissions do not work here. Instead, we use fractional permissions: we put half of the permission for inc_a and half of the permission for inc_b inside the atomic invariant. A thread can then read both variables by opening the atomic invariant, but cannot write them unless it holds the other half of the permission.

This code snippet defines the atomic invariant following our design.

#![allow(unused)]
fn main() {
// The ids to match permissions.
// (`Loc` is vstd's type for the id of a ghost resource: it is what `.id()` returns.)
pub struct CountK {
    pub counter_id: int,
    pub inc_a_id: Loc,
    pub inc_b_id: Loc,
}

// The permission to the real counter, and the invariant's
// half of each of the two ghost increments.
pub struct CountV {
    pub counter_perm: PermissionU32,
    pub inc_a_inv: FracGhost<int>,
    pub inc_b_inv: FracGhost<int>,
}

// The label that names the invariant rule.
pub struct CountInv;

impl InvariantPredicate<CountK, CountV> for CountInv {
    open spec fn inv(k: CountK, v: CountV) -> bool {
        // the permission and the halves belong to the right counter and the right ghost increments
        &&& v.counter_perm.id() == k.counter_id
        &&& v.inc_a_inv.id() == k.inc_a_id
        &&& v.inc_b_inv.id() == k.inc_b_id
        // exactly half of each ghost increment is here (the other half is out with a thread)
        &&& v.inc_a_inv.frac() == 0.5real
        &&& v.inc_b_inv.frac() == 0.5real
        // inc_a and inc_b are each 0 or 1
        &&& 0 <= v.inc_a_inv@ < 2
        &&& 0 <= v.inc_b_inv@ < 2
        // the counter equals inc_a + inc_b
        &&& v.counter_perm.value() == v.inc_a_inv@ + v.inc_b_inv@
    }
}

type Inv = AtomicInvariant<CountK, CountV, CountInv>;
}

Setting up the atomic invariants and ghost resources

Before launching the counter-increment threads, the parent code needs to set up the atomic counter itself (PAtomicU32 and PermissionU32), the fractional ghost increment for each thread, the atomic invariant, and some clones and splits of these to pass to each thread. (The complete program is in my_count_to_2.rs.)

#![allow(unused)]
fn main() {
    // The real counter, shared between the threads.
    let (ptr, Tracked(counter_perm)) = PAtomicU32::new(0);
    let ptr = Arc::new(ptr);

    // Set up Thread A's increment ghost; split it to two halves, one to be kept in
    // the atomic invariant and one to be passed directly to thread A
    let tracked mut inc_a_inv = FracGhost::<int>::new(0);
    let tracked inc_a_thread = inc_a_inv.split();
    let ghost inc_a_id = inc_a_thread.id();

    ... //Set up for Thread B's increment ghost similarly: inc_b_inv, inc_b_thread, ...

    // The shared atomic invariant.
    let tracked inv = Inv::new(
        CountK { counter_id: ptr.id(), inc_a_id: inc_a_inv.id(), inc_b_id: inc_b_inv.id() },
        CountV { counter_perm, inc_a_inv, inc_b_inv },
        0,
    );

    // Clone the invariant and the atomic counter to pass to each thread
    let tracked shared_inv = Shared::new(inv);
    let tracked inv_for_a = shared_inv.clone();
    let ptr_for_a = ptr.clone();
    ... //Similar for Thread B

}

One thread’s counter increment

Here is how we launch a counter-increment thread (thread A).

#![allow(unused)]
fn main() {
    // Thread A: add 1 to the real counter and, in the same atomic step, set inc_a from 0 to 1.
    let thread_a = vstd::thread::spawn(
        move || -> (r: Tracked<FracGhost<int>>)
            ensures
                r@.id() == inc_a_id,
                r@.frac() == 0.5real,
                r@@ == 1,
            {
                // (a closure cannot change a captured variable, so make a `mut` copy)
                let tracked mut inc_a_thread = inc_a_thread;
                open_atomic_invariant!(inv_for_a.borrow() => v => {
                    // the real increment
                    ptr_for_a.fetch_add(Tracked(&mut v.counter_perm), 1);

                    proof {
                        // the ghost update, in the same atomic step:
                        v.inc_a_inv.combine(inc_a_thread);  // join the halves: now we own all of `inc_a`
                        v.inc_a_inv.update(1);  // allowed: we own everything. inc_a: 0 -> 1
                        inc_a_thread = v.inc_a_inv.split();  // split again: each side keeps a half
                    }
                });
                Tracked(inc_a_thread)
            },
    );

    ...
}

There are several things to note in this code:

  • The closure first makes a mut copy of its half, inc_a_thread, because Verus does not yet let a closure change a captured variable directly;
  • Thread A gets to update the atomic counter by borrowing the counter permission v.counter_perm from the atomic invariant, just like in the previous chapter. Here v is the contents of the atomic invariant, taken out for this one atomic step;
  • Thread A combines the half permission v.inc_a_inv living inside the atomic invariant with the half permission inc_a_thread that it holds, and updates its ghost increment (v.inc_a_inv.update(1)) to reflect the fact that it has added 1 to the counter. When the block closes, Verus checks that the rule of the atomic invariant still holds;
  • Thread A returns inc_a_thread at the end so the parent can get its half back;
  • Unlike the previous examples, thread A’s closure has an informative postcondition: the returned half belongs to inc_a and says 1. This postcondition, together with the atomic invariant, allows the parent thread to reason about the value of the counter, as we will see below.

The parent’s conclusion

Once the parent joins the two threads, the postconditions of the two closures allow it to reason about the value of the atomic counter:

fn main() {
    ...

    // The parent joins both threads and gets both halves back, both saying "added".
    if let (Ok(join_a), Ok(join_b)) = (thread_a.join(), thread_b.join()) {
        let Tracked(inc_a_thread) = join_a;
        let Tracked(inc_b_thread) = join_b;
        let n: u32;
        open_atomic_invariant!(shared_inv.borrow() => v => {
            n = ptr.load(Tracked(&v.counter_perm));
            proof {
                // the atomic invariant's halves agree with the halves we hold: inc_a == 1 and inc_b == 1
                v.inc_a_inv.agree(&inc_a_thread);
                v.inc_b_inv.agree(&inc_b_thread);
            }
        });
        // the rule says counter == inc_a + inc_b == 1 + 1
        assert(n == 2);
    }
}

After the joins the parent holds both halves. Inside the atomic invariant, agree shows that the atomic invariant’s halves have the same values as the parent’s halves, so inc_a == 1 and inc_b == 1. The rule gives counter == inc_a + inc_b == 2.

Notice that nobody ever owned the real counter exclusively. The counter stayed shared the whole time. What the parent used was the halves of the ghost increments and the rule that connects them to the counter.

A thread that does not cooperate

Suppose a third thread adds 1 to the counter without owning a half of any ghost increment. To touch the counter, it must open the atomic invariant and take the permission. When it puts the permission back, it must show counter == inc_a + inc_b. It cannot change inc_a or inc_b, because that requires all the ownership of a ghost increment, and it owns none. So the rule fails and Verus rejects the thread.

This is the safety net of the whole scheme: the permission for the counter lives inside the atomic invariant, so everyone who touches the counter must go through the rule.

Why the rule needs 0 <= inc_a < 2

The bound lines may look like decoration. They are not. Delete the two lines 0 <= v.inc_a_inv@ < 2 and 0 <= v.inc_b_inv@ < 2 and Verus reports, once for each thread:

error: precondition not satisfied
    |
    |     ptr_for_a.fetch_add(Tracked(&mut counter_perm), 1);
    |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    |
    = note: failed precondition

fetch_add has a precondition: adding must not overflow the counter’s type. From counter == inc_a + inc_b alone, Verus cannot rule out that the sum is huge. The two bounds give counter <= 2, so there is no overflow. When a proof fails like this, read the failed precondition, ask what fact it needs, and add it to the rule.

A word about PCMs

FracGhost is one example of a PCM (partial commutative monoid, also called a resource algebra). A PCM is a set of values together with a way to combine two of them, where some combinations are not valid. It is a general model of resources, including ghost state: the proof-only resources of this chapter. Iris uses PCMs to express protocols. Given ownership of one particular value, what does the owner know about the global ghost state, and how may the owner update it?

FracGhost is the fractional PCM. Its pieces are a value and a fraction, and combining two pieces adds their fractions, but only when they refer to the same value and the total is at most 1. It exists to keep track of how much of the knowledge about a ghost value has spread among threads, so that once all the pieces are gathered up again, the value can be updated. That gives the three facts this chapter used: two halves of the same ghost value agree on the value (agree), fractions stay in (0, 1], and whoever holds all of it may change it (update).

vstd has the general framework (ResourceAlgebra, PCM) and several ready-made ones: fractions, maps (GhostMapAuth and GhostSubmap), a single variable with an owner (GhostVarAuth and GhostVar), and others. You do not need the general theory to use them. The rule of thumb: when threads must agree on who may change what, give each of them a share of a ghost resource and tie the shares to the real state with an atomic invariant.
