Coordinating threads with ghost resources

In the previous section, an atomic invariant kept a property true in every stable state of a shared variable (i.e., excluding temporary states in the middle of a lock section). However, sometimes we need to reason not only about which states are valid, but also about what exactly the state is and how it evolves from one valid state to another. In the literature, for example in the Iris separation logic (Jung et al., POPL 2015), this further reasoning requires Partial Commutative Monoids (PCMs) that describe protocols on ghost resources.

Fully understanding PCMs and ghost resources goes beyond this tutorial. Here, we give readers a taste of a simple Verus ghost resource type, FracGhost, and build up to a small example: two threads each add 1 to a shared counter that starts at 0, and after both have finished, we want to prove that the counter is exactly 2.

What is FracGhost<T>?

We have seen a few different sharing modes across threads in the last few chapters:

  • Read share. Ordinary Rust data types can be shared across threads only for reading. If the writable ownership is passed to one thread, no other thread can access the variable;
  • Write share. Special Rust data types, like atomic variables and lock-protected data, can be shared across many threads for writing. But there is no read-only version of this sharing: a thread that is given an atomic variable can both load and store, and a thread that is given an RwLock can choose between acquire_read and acquire_write. To let a thread read, we have to give it the ability to write as well;
  • Write share with invariants. Verus’s PAtomic variables and vstd::rwlock::RwLock do not create a new sharing mode. Once a thread is given an atomic invariant or a RwLock, it can update the corresponding data.

These existing sharing schemes are either too restrictive (e.g., read share) or too difficult to reason about. With write share, no thread knows the exact value of the shared data once it releases the lock or closes the atomic invariant. Similarly, the caller that spawns and then joins all the child threads has no idea about the final value of the shared data, except that the value satisfies the invariant.

FracGhost provides a more flexible and more precise way to share ghost data. As with PAtomic and RwLock data, a thread needs a permission to access the ghost data inside a FracGhost. What is unique is that this permission can be split into fractional permissions and shared across threads: only a full permission (frac() == 1) allows a thread to update the ghost data, while a fractional permission only allows reading. Permissions can be split and merged at any time.

Specifically, a t: FracGhost<T> is a proof-only variable. It contains:

  • t.id(): an id. Fractional permissions split from the same ghost resource have the same id;
  • t@, of type T: the value of the ghost data itself;
  • t.frac(): a fraction of ownership / permission, more than 0 and at most 1.

Here is a small example, all of it proof code:

#![allow(unused)]
fn main() {
proof fn frac_ghost_demo() {
    let tracked mut x = FracGhost::new(100int);
    let tracked y = x.split();
    assert(x.frac() == 0.5real);
    assert(y.frac() == 0.5real);
    assert(x@ == 100);
    assert(y@ == 100);
    x.combine(y);
    assert(x.frac() == 1.0real);
    x.update(200);
    assert(x@ == 200);
}
}

When x is just created, it contains the integer value 100 and holds the full permission to that data. The split cuts the permission into two halves: one is kept by x, and the other is given to a new ghost variable y, which shares its id with x. The first four assert statements show that x and y each hold a fraction of 0.5 and both see the value 100. combine puts them back together, and only then, with the combined full permission, can update change the value.

Fractions of the same ghost value can never add up to more than 1. Together with the rule above, this means that at any moment a thread can look at x.frac() to see the sharing status. In particular, when thread A sees x.frac() == 1, A knows that it is the only holder of x, so it can safely claim any details about x in the postcondition of its closure. The code that eventually joins A can trust those claims, because A was the only writer of x.

Before we conclude that FracGhost solves all concurrency problems, note that FracGhost<T> can only represent ghost data. Therefore, we often need a way to connect the value of a fractional ghost variable with a Rust executable variable, because ultimately we want to prove properties of Rust variables. This connection can be made through an AtomicInvariant, as we will see in the example below.

Example: Count to Two

(We took this example from Chris Hawblitzel’s Formal Methods Summer School. His slides explain it in the section on concurrent count-to-2, and his code is a one-file version.)

Two threads, thread A and thread B, each add 1 to a shared counter that starts at 0. After both have finished, the parent wants to prove that the counter is exactly 2.

Why not an atomic invariant. An invariant holds in every state of the shared data, including the starting state, where the counter is 0. So no invariant over the counter can say “the counter is 2”. In this case, the parent thread needs to know exactly what each thread has done to the counter by the time it joins both threads.

Why not the thread’s postcondition. In chapter 23, a fact travels from a thread to its parent through the closure’s postcondition. But a postcondition can only describe what the thread fully owns. Here the counter is shared, and the only permission for it lives in the atomic invariant, so a thread cannot say “I added 1 to the counter” in its postcondition. It can, however, describe a ghost value that it owns. That leads to the next point.

Using fractional ghost resources

With these challenges in mind, a natural thought is to give each thread (A and B) a FracGhost<int> variable, say inc_a and inc_b, to describe how much each thread has added to the counter. We can leverage fractional permissions to make sure that each thread can describe, in its postcondition, what its increment has been. We can then design an atomic invariant so that the parent thread can figure out the value of the counter from the values of the two increments inc_a and inc_b.

There are two parts to designing an atomic invariant: the rule to enforce and the permissions to hold.

The invariant rule is straightforward: the value of the atomic counter (the Rust variable) should equal the sum of the two threads’ increments, inc_a and inc_b (the ghost resources).

The permissions are the tricky part. Following the examples in the previous chapter, we should put the full permission to access the atomic counter here. Then, since the invariant rule depends on the values of inc_a and inc_b, their permissions need to be stored in the atomic invariant as well. However, as discussed above, we want to make sure that thread A cannot update inc_b and thread B cannot update inc_a, so ordinary full permissions do not work here. Instead, we use fractional permissions: we put half of the permission for inc_a and half of the permission for inc_b inside the atomic invariant. A thread can then read both variables by opening the atomic invariant, but cannot write them unless it holds the other half of the permission.

This code snippet defines the atomic invariant following our design.

#![allow(unused)]
fn main() {
// The ids to match permissions.
// (`Loc` is vstd's type for the id of a ghost resource: it is what `.id()` returns.)
pub struct CountK {
    pub counter_id: int,
    pub inc_a_id: Loc,
    pub inc_b_id: Loc,
}

// The permission to the real counter, and the invariant's
// half of each of the two ghost increments.
pub struct CountV {
    pub counter_perm: PermissionU32,
    pub inc_a_inv: FracGhost<int>,
    pub inc_b_inv: FracGhost<int>,
}

// The label that names the invariant rule.
pub struct CountInv;

impl InvariantPredicate<CountK, CountV> for CountInv {
    open spec fn inv(k: CountK, v: CountV) -> bool {
        // the permission and the halves belong to the right counter and the right ghost increments
        &&& v.counter_perm.id() == k.counter_id
        &&& v.inc_a_inv.id() == k.inc_a_id
        &&& v.inc_b_inv.id() == k.inc_b_id
        // exactly half of each ghost increment is here (the other half is out with a thread)
        &&& v.inc_a_inv.frac() == 0.5real
        &&& v.inc_b_inv.frac() == 0.5real
        // inc_a and inc_b are each 0 or 1
        &&& 0 <= v.inc_a_inv@ < 2
        &&& 0 <= v.inc_b_inv@ < 2
        // the counter equals inc_a + inc_b
        &&& v.counter_perm.value() == v.inc_a_inv@ + v.inc_b_inv@
    }
}

type Inv = AtomicInvariant<CountK, CountV, CountInv>;
}

Setting up the atomic invariants and ghost resources

Before launching the counter-increment threads, the parent code needs to set up the atomic counter itself (PAtomicU32 and PermissionU32), the fractional ghost increment for each thread, the atomic invariant, and some clones and splits of these to pass to each thread. (The complete program is in my_count_to_2.rs.)

#![allow(unused)]
fn main() {
    // The real counter, shared between the threads.
    let (ptr, Tracked(counter_perm)) = PAtomicU32::new(0);
    let ptr = Arc::new(ptr);

    // Set up Thread A's increment ghost; split it to two halves, one to be kept in
    // the atomic invariant and one to be passed directly to thread A
    let tracked mut inc_a_inv = FracGhost::<int>::new(0);
    let tracked inc_a_thread = inc_a_inv.split();
    let ghost inc_a_id = inc_a_thread.id();

    ... //Set up for Thread B's increment ghost similarly: inc_b_inv, inc_b_thread, ...

    // The shared atomic invariant.
    let tracked inv = Inv::new(
        CountK { counter_id: ptr.id(), inc_a_id: inc_a_inv.id(), inc_b_id: inc_b_inv.id() },
        CountV { counter_perm, inc_a_inv, inc_b_inv },
        0,
    );

    // Clone the invariant and the atomic counter to pass to each thread
    let tracked shared_inv = Shared::new(inv);
    let tracked inv_for_a = shared_inv.clone();
    let ptr_for_a = ptr.clone();
    ... //Similar for Thread B

}

One thread’s counter increment

Here is how we launch a counter-increment thread (thread A).

#![allow(unused)]
fn main() {
    // Thread A: add 1 to the real counter and, in the same atomic step, set inc_a from 0 to 1.
    let thread_a = vstd::thread::spawn(
        move || -> (r: Tracked<FracGhost<int>>)
            ensures
                r@.id() == inc_a_id,
                r@.frac() == 0.5real,
                r@@ == 1,
            {
                // (a closure cannot change a captured variable, so make a `mut` copy)
                let tracked mut inc_a_thread = inc_a_thread;
                open_atomic_invariant!(inv_for_a.borrow() => v => {
                    // the real increment
                    ptr_for_a.fetch_add(Tracked(&mut v.counter_perm), 1);

                    proof {
                        // the ghost update, in the same atomic step:
                        v.inc_a_inv.combine(inc_a_thread);  // join the halves: now we own all of `inc_a`
                        v.inc_a_inv.update(1);  // allowed: we own everything. inc_a: 0 -> 1
                        inc_a_thread = v.inc_a_inv.split();  // split again: each side keeps a half
                    }
                });
                Tracked(inc_a_thread)
            },
    );

    ...
}

There are several things to note in this code:

  • The closure first makes a mut copy of its half, inc_a_thread, because Verus does not yet let a closure change a captured variable directly;
  • Thread A gets to update the atomic counter by borrowing the counter permission v.counter_perm from the atomic invariant, just like in the previous chapter. Here v is the contents of the atomic invariant, taken out for this one atomic step;
  • Thread A combines the half permission v.inc_a_inv living inside the atomic invariant with the half permission inc_a_thread that it holds, and updates its ghost increment (v.inc_a_inv.update(1)) to reflect the fact that it has added 1 to the counter. When the block closes, Verus checks that the rule of the atomic invariant still holds;
  • Thread A returns inc_a_thread at the end so the parent can get its half back;
  • Unlike the previous examples, thread A’s closure has an informative postcondition: the returned half belongs to inc_a and says 1. This postcondition, together with the atomic invariant, allows the parent thread to reason about the value of the counter, as we will see below.

The parent’s conclusion

Once the parent joins the two threads, the postconditions of the two closures allow it to reason about the value of the atomic counter:

fn main() {
    ...

    // The parent joins both threads and gets both halves back, both saying "added".
    if let (Ok(join_a), Ok(join_b)) = (thread_a.join(), thread_b.join()) {
        let Tracked(inc_a_thread) = join_a;
        let Tracked(inc_b_thread) = join_b;
        let n: u32;
        open_atomic_invariant!(shared_inv.borrow() => v => {
            n = ptr.load(Tracked(&v.counter_perm));
            proof {
                // the atomic invariant's halves agree with the halves we hold: inc_a == 1 and inc_b == 1
                v.inc_a_inv.agree(&inc_a_thread);
                v.inc_b_inv.agree(&inc_b_thread);
            }
        });
        // the rule says counter == inc_a + inc_b == 1 + 1
        assert(n == 2);
    }
}

After the joins the parent holds both halves. Inside the atomic invariant, agree shows that the atomic invariant’s halves have the same values as the parent’s halves, so inc_a == 1 and inc_b == 1. The rule gives counter == inc_a + inc_b == 2.

Notice that nobody ever owned the real counter exclusively. The counter stayed shared the whole time. What the parent used was the halves of the ghost increments and the rule that connects them to the counter.

A thread that does not cooperate

Suppose a third thread adds 1 to the counter without owning a half of any ghost increment. To touch the counter, it must open the atomic invariant and take the permission. When it puts the permission back, it must show counter == inc_a + inc_b. It cannot change inc_a or inc_b, because that requires all the ownership of a ghost increment, and it owns none. So the rule fails and Verus rejects the thread.

This is the safety net of the whole scheme: the permission for the counter lives inside the atomic invariant, so everyone who touches the counter must go through the rule.

Why the rule needs 0 <= inc_a < 2

The bound lines may look like decoration. They are not. Delete the two lines 0 <= v.inc_a_inv@ < 2 and 0 <= v.inc_b_inv@ < 2 and Verus reports, once for each thread:

error: precondition not satisfied
    |
    |     ptr_for_a.fetch_add(Tracked(&mut counter_perm), 1);
    |     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    |
    = note: failed precondition

fetch_add has a precondition: adding must not overflow the counter’s type. From counter == inc_a + inc_b alone, Verus cannot rule out that the sum is huge. The two bounds give counter <= 2, so there is no overflow. When a proof fails like this, read the failed precondition, ask what fact it needs, and add it to the rule.

A word about PCMs

FracGhost is one example of a PCM (partial commutative monoid, also called a resource algebra). A PCM is a set of values together with a way to combine two of them, where some combinations are not valid. It is a general model of resources, including ghost state: the proof-only resources of this chapter. Iris uses PCMs to express protocols. Given ownership of one particular value, what does the owner know about the global ghost state, and how may the owner update it?

FracGhost is the fractional PCM. Its pieces are a value and a fraction, and combining two pieces adds their fractions, but only when they refer to the same value and the total is at most 1. It exists to keep track of how much of the knowledge about a ghost value has spread among threads, so that once all the pieces are gathered up again, the value can be updated. That gives the three facts this chapter used: two halves of the same ghost value agree on the value (agree), fractions stay in (0, 1], and whoever holds all of it may change it (update).

vstd has the general framework (ResourceAlgebra, PCM) and several ready-made ones: fractions, maps (GhostMapAuth and GhostSubmap), a single variable with an owner (GhostVarAuth and GhostVar), and others. You do not need the general theory to use them. The rule of thumb: when threads must agree on who may change what, give each of them a share of a ghost resource and tie the shares to the real state with an atomic invariant.
