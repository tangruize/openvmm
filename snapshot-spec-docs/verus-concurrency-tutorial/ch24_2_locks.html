Atomic Invariants for Lock-Protected Data

The previous section explained how to use atomic invariants to reason about concurrent updates to atomic variables. However, an atomic variable holds only one machine word, and an atomic instruction changes only one variable at a time, so Rust threads need other means, such as locks, to share larger data with each other.

This section explains how to use the idea of atomic invariants to reason about lock-protected data. We use the same running example as before, the tight window [lo, hi] with the rule lo <= hi. The complete program is in my_rwlock_window.rs.

Rust locks and their inherent permissions

In Rust, a lock that protects data of type V is written RwLock<V>, Mutex<V>, and so on. Conceptually, a lock is very much like a permission: lock-protected data can only be accessed when the corresponding lock is held. To avoid bugs, it is often helpful to think about which properties the lock-protected data maintains at the boundaries of lock critical sections. Those properties may be violated in the middle of a critical section (i.e., after the lock is acquired and before it is released), but they must be restored right before the lock is released.

Here is how one uses Rust’s std::sync::RwLock to implement the widen_down operation from the previous section. Note that lo and hi are no longer two separate atomic variables: they are now protected by the same lock.

#![allow(unused)]
fn main() {
struct Window {
    lo: u64,
    hi: u64,
}

...

fn widen_down(lock: &RwLock<Window>, n: u64) {
    let mut w = lock.write().unwrap(); // guard: blocks until we hold the lock
    if n < w.lo {
        w.lo = n;
    }
} // the guard is dropped here, and that releases the lock automatically
}

The lock in vstd that embodies atomic invariants

Verus’s read-write lock has the type vstd::rwlock::RwLock<V, Pred>. It is similar to Rust’s std::sync::RwLock<V> in that it owns shared data of type V, which cannot be accessed unless the lock is acquired. It differs in that it also owns a rule, given by Pred. This rule defines a property of the shared data that holds when the lock has just been acquired and must hold again when the lock is released.

The code below defines a RwLockPredicate named LoLeHi whose rule says that the lo field should be less than or equal to the hi field of the Window object. LoLeHi then helps define a vstd read-write lock type Lock that owns a shared Window object and enforces the LoLeHi rule on that object.

#![allow(unused)]
fn main() {
pub struct Window {
    pub lo: u64,
    pub hi: u64,
}

pub struct LoLeHi;

impl RwLockPredicate<Window> for LoLeHi {
    open spec fn inv(self, w: Window) -> bool {
        w.lo <= w.hi
    }
}

type Lock = RwLock<Window, LoLeHi>;
}

As we can see, vstd::rwlock::RwLock hides the complexity of permissions, atomic invariants, and so on, so that we can use it in a way very similar to Rust’s locks. Readers who are interested in the implementation can refer to vstd/rwlock.rs.

Updating data protected by vstd::rwlock::RwLock

It is very easy to rewrite the widen_down function to use vstd::rwlock::RwLock, as follows:

#![allow(unused)]
fn main() {
pub fn widen_down(lock: &Lock, n: u64) {
    let (mut w, handle) = lock.acquire_write(); // blocks until we hold the lock
    if n < w.lo {
        w.lo = n;
    }
    handle.release_write(w); // unlike std's lock, the release is an explicit call
}
}

Verus will verify that the property w.lo <= w.hi holds right before the lock is released.

Lock operations that atomics cannot do

In the previous section, the widen function needs two atomic instructions, lo.fetch_min and then hi.fetch_max, and Verus has to prove that the invariant holds right after each of them. With a lock, widen can be done in a single critical section, as follows, and Verus only needs to prove that the invariant holds once, at the end of the critical section.

#![allow(unused)]
fn main() {
pub fn widen(lock: &Lock, n: u64) {
    let (mut w, handle) = lock.acquire_write();
    if n < w.lo {
        w.lo = n; //widen down
    } else if n > w.hi {
        w.hi = n; //widen up
    }
    handle.release_write(w);
}
}

Of course, in this case the invariant holds with atomic variables and with locks alike. However, there are cases where the invariant cannot be proved when the implementation uses atomic variables.

Imagine an operation that replaces the window with a new [a, b], where a <= b. The implementation with a lock is straightforward:

#![allow(unused)]
fn main() {
// Replace the window with [a, b].
pub fn reset_to(lock: &Lock, a: u64, b: u64)
    requires
        a <= b,
{
    let (mut w, handle) = lock.acquire_write();
    w.lo = a;
    // lo <= hi is BROKEN here if a > the old hi (e.g. [20, 30] -> lo = 50 gives [50, 30]).
    // Under the lock nobody else can see this state, so it is fine.
    w.hi = b;
    // lo = a <= b = hi: the invariant holds again, and release_write checks exactly that.
    handle.release_write(w);
}
}

Unfortunately, it is not possible to implement this operation correctly with two separate atomic variables and plain writes. Imagine that the old window was [20, 30] and the new window [a, b] is [50, 60]. The invariant lo <= hi is broken when we update lo to a: the window temporarily becomes [50, 30]. With a lock, this is not a problem, because no other thread can see this temporary state, so the invariant only needs to be re-established right before the lock is released. With atomic variables, the invariant would be violated at that moment, and the code would be buggy, because other threads could update lo or hi while the window has the invalid value [50, 30].

Sharing the lock-protected variable between threads

Threads share the lock through an Arc; at any time, the parent thread or one of the child threads can read both Window fields inside a lock critical section:

#![allow(unused)]
fn main() {
fn run_threads() -> (out: (u64, u64))
    ensures
        out.0 <= out.1,
{
    ...

    // Both fields are read in one critical section, so they are consistent.
    let handle = lock.acquire_read();
    let w = handle.borrow();
    let result = (w.lo, w.hi);
    handle.release_read();
    result
}
}

The function run_threads promises out.0 <= out.1, and this time the promise is about two numbers that the program really holds, unlike in the previous section.

When the rule is broken

Remove the line w.hi = b; from reset_to. Now the data is left as [a, old_hi], which may break the rule. Verus rejects the program at the release:

error: precondition not satisfied
   |
   |     handle.release_write(w);
   |     ^^^^^^^^^^^^^^^^^^^^^^^
   |
   = note: failed precondition

The failed precondition is release_write’s requires: the rule must hold for the data being put back. Everything before that line was allowed.

What is and is not proved

  • Verus does not check that you release the lock. A handle is not released when it is dropped, and a forgotten release_write would hang the program. So this proves the rule, not the absence of deadlock.
  • vstd::rwlock::RwLock waits by spinning, which is simple but can be slow when many threads compete.
  • vstd has no specification for std::sync::Mutex. The vstd lock is a replacement, not a wrapper, so verifying code that already uses std locks means either switching to the vstd lock or writing a trusted specification yourself.
