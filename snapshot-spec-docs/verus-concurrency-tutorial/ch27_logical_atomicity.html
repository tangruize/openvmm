Logical atomicity

This feature is experimental. Everything in this chapter is implemented and tested in the latest release, but the feature is still being developed and some details may change.

In short: logical atomicity lets a function that performs several atomic steps behave, for the purposes of a proof, as if it were one step. It is the tool for writing a library function that works for many different users, each with their own invariant.

This is the most advanced chapter of the concurrency part. It builds on chapter 24 (atomic invariants) and, for the example in the second half, on the tickets of chapter 26.

The problem

In chapter 24 we wrote “add 2” with a compare-and-swap loop:

#![allow(unused)]
fn main() {
// Add 2 with a compare-and-swap loop.
pub fn add_two(x: &PAtomicU64, Tracked(inv): Tracked<&Inv>)
    requires
        inv.constant() == x.id(),
{
    // step 1: read the current value
    let mut curr;
    open_atomic_invariant!(inv => perm => {
        curr = x.load(Tracked(&perm));
    });

    loop {
        let next = curr.wrapping_add(2);
        // step 2: swap `next` in, but only if the value is still `curr`
        let res;
        open_atomic_invariant!(inv => perm => {
            res = x.compare_exchange_weak(Tracked(&mut perm), curr, next);
        });
        match res {
            Ok(_) => {
                return ;
            },
            // somebody changed the counter first: `new` is its latest value, try again
            Err(new) => {
                curr = new;
            },
        }
    }
}
}

It works, but look at what it needs: the box. It opens the box by itself, around each atomic step, so it is written for one particular box and one particular rule (“always even”).

Now suppose that add_two is part of a library, and two different programs use it:

  • program A keeps its counter in a box whose rule is “the counter is even”;
  • program B keeps its counter in a different box, which also holds a ticket, and whose rule is “the counter equals a ghost number that B updates at every add”.

The library author cannot know either box. With the style of chapter 24 the library would need one copy of add_two per user. We want a single add_two that both can use.

Why not just pass the key?

The first idea is to hand the function the key as a parameter. That works for a function with one atomic step. The key is borrowed from the box for that one step, and nobody else can interfere. (The guide’s section on #[verifier::atomic] describes this case.)

It does not work for several steps. Passing the key into the function means holding it for the whole call, and a box can only be opened for one atomic step. And if the caller kept the key for the whole call, no other thread could use the variable meanwhile, which defeats the purpose.

Between its steps, other threads run and change the variable. So the function has to get the key back from the box each time it needs it. But it cannot open a box it does not know.

The idea: ask for the key at the right moment

An atomic specification lets the function say to its caller: “when I reach the moment where my call takes effect, give me the key, and I will return it changed.”

The caller supplies a little piece of proof code for that moment. In that code, the caller opens its own box, hands the key over, takes it back, and closes the box again. The function never learns what the box is.

The moment that counts: the linearization point

A function with several atomic steps usually has one step where its effect really happens. In the compare-and-swap loop it is the swap that succeeds. The earlier steps (the first read and the failed swaps) change nothing. That decisive step is called the linearization point.

An atomic specification describes the function as if it happened at that instant. It talks about four points in time:

pointwhen
function preconditionat the start of the call
atomic preconditionjust before the linearization point
atomic postconditionjust after the linearization point
function postconditionat the end of the call

The atomic pre- and postcondition describe the key: what it looks like just before and just after the step. The ordinary pre- and postcondition describe the call as a whole.

The simplest case: one step, always committed

Start with a function that cannot fail: reset the variable to 0, with a single store.

#![allow(unused)]
fn main() {
// The simplest atomic specification: ONE atomic step, and the update is always committed.
pub fn reset(var: &PAtomicU64)
    atomically (atomic_update) {
        (perm: PermissionU64) -> (commit: Commit<PermissionU64>),
        requires
            perm@.patomic == var.id(),
        ensures
            commit@@.patomic == perm@.patomic,
            commit@@.value == 0,
        outer_mask any,
        inner_mask none,
    },
{
    try_open_atomic_update!(atomic_update, mut perm => {
        var.store(Tracked(&mut perm), 0);
        Tracked(Commit(perm))
    });
    assert(atomic_update.resolves());
}
}

The shape of the specification:

atomically (atomic_update) {
    (input) -> (output),
    requires  <atomic precondition>,
    ensures   <atomic postcondition>,
    outer_mask any,
    inner_mask none,
}
  • atomically (atomic_update) { ... } marks the function as logically atomic. atomic_update is a name for a proof-only object that stands for the moment of the step. (You can pick any name; we always use atomic_update.) Its type is AtomicUpdate<...>.
  • (perm: PermissionU64) -> (commit: Commit<PermissionU64>) says what is exchanged at the moment: the caller hands over a key perm, and gets back a key commit. Both are proof-only.
  • requires is the atomic precondition: what the key looks like just before. Here, that it is the key to our variable var.
  • ensures is the atomic postcondition: what it looks like after. Here, that it belongs to the same variable and holds the value 0.
  • Commit<...> means that this update is always carried out; it can never be given up.
  • The masks say which boxes the caller’s code may open. any and none are what you want almost every time: the caller may open any box, and the function’s own step opens none.

The body asks for the key with try_open_atomic_update!. Inside its braces the key is available as perm, we do the real atomic operation, and we return the new key. The last line checks that the update has been used up:

  • Inside the macro: store(0) happens, and Commit(perm) hands the changed key back.
  • After the macro: atomic_update.resolves() says that the update has been carried out. Verus requires you to show it before the function returns. (It is one of three proof-only facts about the update: resolves(), input() and output().)

How the caller uses it

The caller writes the proof code for the moment, in an atomically block. Here is owner A from the problem above, whose box says “always even”:

#![allow(unused)]
fn main() {
pub struct EvenInv;

impl InvariantPredicate<int, PermissionU64> for EvenInv {
    open spec fn inv(x_id: int, perm: PermissionU64) -> bool {
        &&& perm@.patomic == x_id
        &&& perm@.value % 2 == 0
    }
}

type InvA = AtomicInvariant<int, PermissionU64, EvenInv>;
}
#![allow(unused)]
fn main() {
// Owner A's wrapper for `reset`: no loop, because the update cannot be aborted.
fn reset_even(x: &PAtomicU64, Tracked(inv): Tracked<&InvA>)
    requires
        inv.constant() == x.id(),
{
    let Tracked(credit) = vstd::invariant::create_open_invariant_credit();
    reset(x) atomically |update| {
        open_atomic_invariant!(credit => inv => perm => {
            perm = Commit::get(update(perm));
        });
    };
}
}
  • reset(x) atomically |update| { ... } calls reset and supplies the code for the moment. update is a proof-only function that stands for the step: call it with the key and you get the changed key back.
  • Inside, the caller opens its own box with open_atomic_invariant!, takes the key out as perm, calls update(perm), and puts the result back. At the closing brace Verus checks the caller’s rule: after a reset the value is 0, which is even.
  • The block is proof code. Opening a box in proof code costs one credit, a proof-only coin (credit) created just before. We will see more of credits below.

That is the whole idea. The function and the box are connected only through the key.

When the function must look first: the abort case

reset was easy because its only step is the decisive one. A compare-and-swap loop is harder:

  • the first read has to look at the variable without taking effect;
  • each failed swap also looks at the variable and takes no effect;
  • only the final successful swap is the linearization point.

To look, the function needs the key, but it must give it back unchanged and keep the right to ask again later. So an atomic update can also be aborted: the function opens the update, looks, and gives it back, and gets the update itself back to open again.

The output type says whether a given answer commits or aborts. Commit<T> can only commit. Result<T, E> commits with Ok(t) and aborts with Err(e). (Technically the output type implements a trait called UpdateTry, which sorts values into “commit” and “abort”.)

Here is the specification of add_two:

#![allow(unused)]
fn main() {
pub fn add_two(var: &PAtomicU64) -> (out: u64)
    atomically (atomic_update) {
        (perm: PermissionU64) -> (res: Result<PermissionU64, (PermissionU64, OpenInvariantCredit)>),
        requires
            perm@.patomic == var.id(),
        ensures match res {
            Err((p, _)) => p@ == perm@,
            Ok(p) => {
                &&& p@.patomic == perm@.patomic
                &&& p@.value == perm@.value.wrapping_add(2)
            }
        },
        outer_mask any,
        inner_mask none,
    },
    ensures
        out == perm@.value,
{
}
  • Ok(p): a commit. The new key p has the old value plus 2.
  • Err((p, _)): an abort. The key comes back unchanged (p@ == perm@), together with an OpenInvariantCredit (we explain it next).
  • The ordinary postcondition out == perm@.value says that the function returns the value the variable had at the linearization point. Here perm is the key that the caller hands over at the moment of the commit.

Here is the whole function:

#![allow(unused)]
fn main() {
pub fn add_two(var: &PAtomicU64) -> (out: u64)
    atomically (atomic_update) {
        (perm: PermissionU64) -> (res: Result<PermissionU64, (PermissionU64, OpenInvariantCredit)>),
        requires
            perm@.patomic == var.id(),
        ensures match res {
            Err((p, _)) => p@ == perm@,
            Ok(p) => {
                &&& p@.patomic == perm@.patomic
                &&& p@.value == perm@.value.wrapping_add(2)
            }
        },
        outer_mask any,
        inner_mask none,
    },
    ensures
        out == perm@.value,
{
    let Tracked(credit) = vstd::invariant::create_open_invariant_credit();
    let tracked mut au = atomic_update;

    // the first read: open the update, look at the value, and give it back unchanged (abort)
    let mut curr;
    let wrapped_au = try_open_atomic_update!(au, perm => {
        curr = var.load(Tracked(&perm));
        Tracked(Err((perm, credit)))
    });
    proof { au = wrapped_au.get().tracked_unwrap_err() };

    loop invariant au == atomic_update {
        let Tracked(credit) = vstd::invariant::create_open_invariant_credit();
        let next = curr.wrapping_add(2);

        // try to swap the new value in; commit the update if it worked, abort if not
        let res;
        let maybe_au = try_open_atomic_update!(au, mut perm => {
            res = var.compare_exchange_weak(Tracked(&mut perm), curr, next);
            Tracked(match res {
                Ok(_) => Ok(perm),
                Err(_) => Err((perm, credit)),
            })
        });

        match res {
            Ok(_) => {
                assert(atomic_update.resolves());
                return curr;
            },
            Err(new) => {
                proof { au = maybe_au.get().tracked_unwrap_err() };
                curr = new;
            },
        }
    }
}
}
  • The first try_open_atomic_update! reads the value and aborts: it returns Err((perm, credit)), the key unchanged. The result wrapped_au contains the update back, and we take it out into au.
  • In the loop, each round tries compare_exchange_weak. If the swap worked we return Ok(perm) (a commit). If not we return Err((perm, credit)) (an abort) and go around again.
  • After a commit, atomic_update.resolves() holds, and the function returns.
  • The loop invariant au == atomic_update says that we still hold the same update each time round the loop. (loop_isolation(false) at the top of the file lets Verus carry other facts into the loop; it is not important for the idea.)

Credits

Why does an abort hand a credit back? The caller’s code for the moment is proof code, and opening a box in proof code costs one credit. The caller starts with one credit. The function may ask for the key many times (every abort asks the caller to run its code again), and each time the caller needs a credit to open its box. So every abort returns the credit that the caller just spent, ready for the next round.

Calling a function with an abort case

Because the function may ask again, the caller’s code has to be a loop. Owner A’s wrapper:

#![allow(unused)]
fn main() {
// Owner A's wrapper: it opens ITS OWN invariant inside `update`.
fn add_two_even(x: &PAtomicU64, Tracked(inv): Tracked<&InvA>)
    requires
        inv.constant() == x.id(),
{
    let Tracked(mut credit) = vstd::invariant::create_open_invariant_credit();
    add_two(x) atomically loop |update| {
        let tracked mut spare = None;
        open_atomic_invariant!(credit => inv => perm => {
            let tracked res: Result<PermissionU64, (PermissionU64, OpenInvariantCredit)> =
                update(perm);
            match res {
                Ok(p) => perm = p,
                Err((p, c)) => {
                    perm = p;
                    spare = Some(c);
                },
            }
        });
        match spare {
            None => break,
            Some(c) => credit = c,
        }
    };
}
}
  • add_two(x) atomically loop |update| { ... } calls the function and supplies the code for the moment. This code runs every time the function asks for the key.
  • Inside, the caller opens its box, calls update(perm), and looks at the answer. Ok(p) means the update was committed: the caller puts p back and the code breaks out. Err((p, c)) means an abort: the caller puts the key back, keeps the returned credit c for the next round, and the loop goes round again.
  • Verus checks that break happens only after a commit and that the loop continues only after an abort.
  • When the update is Commit<...>, there is nothing to repeat, so the word loop is left out, as in reset_even above.

Two owners, one function

Now owner B. Its box holds the key and a ticket (a GhostVarAuth, the box’s half of a ghost number that B holds the other half of). The rule says that the counter equals that number:

#![allow(unused)]
fn main() {
pub struct KB {
    pub x_id: int,
    pub gv_id: Loc,
}

pub struct VB {
    pub perm: PermissionU64,
    pub auth: GhostVarAuth<u64>,
}

pub struct MirrorInv;

impl InvariantPredicate<KB, VB> for MirrorInv {
    open spec fn inv(k: KB, v: VB) -> bool {
        &&& v.perm@.patomic == k.x_id
        &&& v.auth.id() == k.gv_id
        &&& v.perm@.value == v.auth@  // the counter equals the ghost number
    }
}

type InvB = AtomicInvariant<KB, VB, MirrorInv>;
}

B’s wrapper calls the same add_two. In the code for the moment it also moves B’s ticket to the new value, in the same step as the add:

#![allow(unused)]
fn main() {
// Owner B's wrapper around the SAME `add_two`: it opens ITS (different) invariant inside
// `update`, and moves its ticket to the new value at that instant.
fn add_two_tracked(x: &PAtomicU64, Tracked(inv): Tracked<&InvB>, Tracked(ticket): Tracked<&mut GhostVar<u64>>) -> (out: u64)
    requires
        inv.constant().x_id == x.id(),
        inv.constant().gv_id == old(ticket).id(),
    ensures
        final(ticket).id() == old(ticket).id(),
        out == old(ticket)@,
        final(ticket)@ == old(ticket)@.wrapping_add(2),
{
    let Tracked(mut credit) = vstd::invariant::create_open_invariant_credit();
    let ghost start = ticket@;
    let ghost ticket_id = ticket.id();
    let out = add_two(x) atomically loop |update|
        invariant
            ticket.id() == ticket_id,
            ticket@ == start,
            inv.constant().gv_id == ticket_id,
    {
        let tracked mut spare = None;
        open_atomic_invariant!(credit => inv => v => {
            let tracked VB { perm, mut auth } = v;
            auth.agree(&*ticket);
            let tracked res: Result<PermissionU64, (PermissionU64, OpenInvariantCredit)> =
                update(perm);
            match res {
                Ok(p) => {
                    auth.update(ticket, p@.value);
                    v = VB { perm: p, auth };
                },
                Err((p, c)) => {
                    v = VB { perm: p, auth };
                    spare = Some(c);
                },
            }
        });
        match spare {
            None => break,
            Some(c) => credit = c,
        }
    };
    out
}
}

B gets a real postcondition: the call returns the old value of B’s number, and afterwards B’s ticket says that number plus 2. Check it by calling the wrapper twice:

#![allow(unused)]
fn main() {
fn owner_b() {
    let (x, Tracked(perm)) = PAtomicU64::new(0);
    let tracked (auth, mut ticket) = GhostVarAuth::new(0u64);
    let tracked inv = InvB::new(KB { x_id: x.id(), gv_id: auth.id() }, VB { perm, auth }, 1);

    let a = add_two_tracked(&x, Tracked(&inv), Tracked(&mut ticket));
    let b = add_two_tracked(&x, Tracked(&inv), Tracked(&mut ticket));

    assert(a == 0);
    assert(b == 2);
    assert(ticket@ == 4);
}
}

Owner A and owner B have different boxes and different rules, yet add_two was written once and never saw either. That is what logical atomicity buys.

When you get it wrong

Suppose the successful swap aborted instead of committing (that is, Ok(_) returned Err((perm, credit))). Verus rejects the function:

error: assertion failed
  --> f27.rs:75:24
   |
75 |                 assert(atomic_update.resolves());
   |                        ^^^^^^^^^^^^^^^^^^^^^^^^ assertion failed

error: cannot show atomic postcondition hold at end of block
  --> f27.rs:65:24
   |
65 |           let maybe_au = try_open_atomic_update!(au, mut perm => {
   |  ________________________^
...

There are two complaints. The update was never committed, so resolves() fails. And an abort promises that the key comes back unchanged, but the swap changed the value, so that promise is false. The linearization point has to be a commit.

How this relates to invariants

Atomic specifications and atomic invariants are separate features. You can use either without the other:

  • An invariant only (chapter 24) is enough when you want a rule that holds in every state, and the function that changes the variable can be written knowing the rule.
  • An atomic specification is for a function with several steps that must work for many different owners, or that must describe what it does at one instant.

An atomic specification can also be used with no box at all: a caller that owns the key directly (not in a shared box) just passes it to update, with no open_atomic_invariant!.

The abort case and the requirement to commit exactly once are what make the technique work for loops, as in the compare-and-swap loop above.

Related work

Logical atomicity comes from separation logic. There are two common styles, named after the systems that introduced them.

  • HOCAP style (Jacobs and Piessens, POPL’11; Svendsen et al., ESOP’13). The function takes a callback, a piece of proof code that it calls at the linearization point. Verus has this in vstd::logatom, and it was used to verify CapybaraKV (LeBlanc et al., OSDI’25). It needs a lot of boilerplate, the callback is a higher-order object that is hard to read, and it can only update ghost state at the linearization point.
  • TaDA style (da Rocha Pinto et al., ECOOP’14; Iris, Jung et al., POPL’15). The function has an atomic specification, as in this chapter. This is what Verus’s atomically is based on.

For a larger example in which one thread finishes the work of another (called helping), see examples/helping.rs: two concurrent calls to flip hand their atomic updates to each other through an invariant and cancel out.

What is and is not proved

  • add_two returns the value the variable had at one instant, and at that instant the value changed by exactly 2. This holds in every interleaving.
  • Each owner’s rule holds in every state. Owner B also learns exactly how its ticket moved.
  • The function itself does not check, and cannot check, the owners’ rules. Each owner proves its own rule in its own code.
  • It does not claim that the function terminates: a thread may keep failing its swap. The loop needs exec_allows_no_decreases_clause for that reason.
