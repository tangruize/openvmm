Atomic Invariants for Atomic Variables

This section applies the idea of atomic invariants to Rust’s atomic variables. We explain how to create a permission for an atomic variable, how to define the invariant rule, and how to open and close the atomic invariant.

The atomic variable and its permission

A challenge in applying atomic invariants to atomic variables is that, in Rust, atomic variables are not associated with permissions: any thread that receives a clone of an Arc holding an atomic variable can update it at any time. Therefore, vstd provides a wrapper for every Rust atomic type that introduces permissions. In the rest of this section we use PAtomicU64, the vstd wrapper for the Rust type AtomicU64, in our examples. The details of these wrapper types can be found in vstd/atomic.rs.

PAtomicU64 is a wrapper around AtomicU64. All the APIs of AtomicU64, such as load, store, fetch_add, compare_exchange, and many others, also exist for PAtomicU64. The main difference is that AtomicU64::new(..) returns one value, the atomic variable of type AtomicU64, while PAtomicU64::new(..) returns two: the atomic variable, of type PAtomicU64, and the permission associated with it, of type PermissionU64, as shown below.

#![allow(unused)]
fn main() {
  let (x, Tracked(mut perm)) = PAtomicU64::new(0);
}

There are two useful properties relating the atomic variable x and its corresponding permission perm:

  • perm.id() equals x.id(): each of them has an integer id, and the ids are used to match them with each other. In addition, all the APIs that read or write the atomic data take an extra ghost parameter in PAtomicU64: the permission. They have a precondition saying that the permission passed in must be the permission of this very atomic variable.
  • perm.value() always matches the u64 value stored inside x. This relationship is maintained automatically by the PAtomicU64 APIs, and it is crucial for our verification. In fact, atomic invariants describe properties held by the tracked ghost variable perm, not directly by x.

Here is an example that creates a PAtomicU64 counter whose initial value is 0 and then uses its permission to update the value to 11.

#![allow(unused)]
fn main() {
fn permission_demo() {
    let (x, Tracked(mut perm)) = PAtomicU64::new(0);
    x.store(Tracked(&mut perm), 11);
    let v = x.load(Tracked(&perm));
    assert(v == 11);
}
}

Here one function owns the permission, so nothing else is needed. With several threads the permission has to be shared, which is what the rest of this section is about.

The rule: InvariantPredicate

vstd provides a trait InvariantPredicate<K, V> to specify the invariant rule. This trait is useful not only for AtomicInvariant, but also for LocalInvariant (an invariant that is not shared between threads; see vstd/invariant.rs), for the RwLock that section 24.2 introduces (see vstd/rwlock.rs), and for the atomic_ghost types (see vstd/atomic_ghost.rs).

#![allow(unused)]
fn main() {
pub trait InvariantPredicate<K, V> {
    spec fn inv(k: K, v: V) -> bool;
}
}

In general, k is an (optional) constant that helps define the invariant rule, and v is the variable that is supposed to satisfy the invariant.

In the code below, EvenInv describes an invariant that a permission perm must satisfy: perm must correspond to a specific atomic variable (perm.id() == x_id), and the value associated with the permission must be an even number (perm.value() % 2 == 0).

#![allow(unused)]
fn main() {
pub struct EvenInv;

impl InvariantPredicate<int, PermissionU64> for EvenInv {
    open spec fn inv(x_id: int, perm: PermissionU64) -> bool {
        &&& perm.id() == x_id  // the permission belongs to our atomic variable
        &&& perm.value() % 2 == 0  // the property we care about
    }
}
}

The AtomicInvariant type

Now we can look at the atomic invariant type in Verus.

AtomicInvariant<K, V, Pred> is a proof-only generic type. An object of this type holds a constant of type K and a variable of type V. The type Pred, which implements InvariantPredicate<K, V>, supplies the rule inv that every state of the variable must satisfy.

In the example here, we define an AtomicInvariant type Inv. An Inv object will hold a permission of type PermissionU64, and the permission has to satisfy the rule specified by EvenInv: the permission corresponds to a specific atomic variable identified by an x_id of type int (i.e., type K is int), and the value of the permission is always even.

#![allow(unused)]
fn main() {
    type Inv = AtomicInvariant<int, PermissionU64, EvenInv>;

    ...

    let (x, Tracked(perm)) = PAtomicU64::new(0);
    let tracked inv = Inv::new(x.id(), perm, 1);
    let x = Arc::new(x);
    let inv = Arc::new(Tracked(inv));
}

Note that the code above also shows how a parent thread prepares the atomic variable x and the atomic invariant inv, both wrapped in Arcs so that they can be shared. Later on, every thread can get a clone of x and a clone of inv, which contains the permission to update x.

  • x.id() is the variable’s id, which is used to match its corresponding permission.
  • Inv::new(x.id(), perm, 1) creates the atomic invariant. It takes the constant (the id), the contents (the permission), and a number called the namespace, which you can ignore for now.

Creating the atomic invariant checks that inv holds for the starting contents: the value 0 is even, and x.id() matches perm.id().

Atomic updates to an atomic variable using a permission

As we have seen, if a thread wants to update an atomic variable x: PAtomicU64, it has to obtain the corresponding permission, which is owned by an atomic invariant inv.

Verus provides a macro open_atomic_invariant! to open an atomic invariant, take the permission out, perform one atomic update, and put the permission back: open_atomic_invariant!(invariant => permission => {/*atomic update that uses the permission*/});. Right before the atomic update, we can assume that the invariant rule holds; at the end of the update, Verus needs to prove that the rule still holds.

Here is an example of atomically adding 2 to an atomic counter; its complete program is in my_atomic_counter_fetch_add.rs:

#![allow(unused)]
fn main() {
// One physical step (fetch_add), so one open/close of the invariant.
pub fn add_two(x: &PAtomicU64, Tracked(inv): Tracked<&Inv>)
    requires
        inv.constant() == x.id(),
{
    open_atomic_invariant!(inv => perm => {
        x.fetch_add_wrapping(Tracked(&mut perm), 2);
    });
}
}
  • The requires line says that the invariant passed into add_two has to be the one for the atomic variable x.
  • open_atomic_invariant!(inv => perm => { ... }) takes the permission perm out of the atomic invariant inv. At the closing brace the permission goes back into the invariant, and Verus checks that the invariant rule still holds.
  • Only one atomic operation is allowed between the braces.

Where is the proof? None is needed here. At the closing brace Verus must show that the new value is even. It knows two things: the old value was even (the rule, assumed when inv was opened), and the instruction added 2. Adding 2 to an even number gives an even number, and Verus’s solver sees that on its own.

Here is another atomic operation, which also uses the permission from the atomic invariant temporarily:

#![allow(unused)]
fn main() {
// One physical step (store), so one open/close of the invariant.
pub fn reset(x: &PAtomicU64, Tracked(inv): Tracked<&Inv>)
    requires
        inv.constant() == x.id(),
{
    open_atomic_invariant!(inv => perm => {
        x.store(Tracked(&mut perm), 0);
    });
}
}

Sharing the variable and the atomic invariant between threads

As we mentioned briefly above, to give every thread access to the variable and the atomic invariant, each goes into an Arc, and every thread gets its own clone of both.

#![allow(unused)]
fn main() {
fn spawn_adder(x: &Arc<PAtomicU64>, inv: &Arc<Tracked<Inv>>) -> (h: JoinHandle<()>)
    requires
        inv@.constant() == x.id(),
{
    let (x, inv) = (x.clone(), inv.clone());
    spawn(move || -> (r: ()) { add_two(&x, Tracked(inv.borrow())) })
}
}

Now we can tie everything together in the run_threads function below. It creates the counter and the atomic invariant, shares both with four threads (two that add 2 and two that reset to 0), waits for all of them, and then reads the counter by opening the atomic invariant once more:

#![allow(unused)]
fn main() {
fn run_threads() -> (out: Result<u64, ()>)
    ensures
        out is Ok ==> out.unwrap() % 2 == 0,
{
    let (x, Tracked(perm)) = PAtomicU64::new(0);
    let tracked inv = Inv::new(x.id(), perm, 1);
    let x = Arc::new(x);
    let inv = Arc::new(Tracked(inv));

    let a0 = spawn_adder(&x, &inv);
    let a1 = spawn_adder(&x, &inv);

    let r0 = spawn_resetter(&x, &inv);
    let r1 = spawn_resetter(&x, &inv);

    let ok = a0.join().is_ok() && a1.join().is_ok() && r0.join().is_ok() && r1.join().is_ok();

    if ok {
        let result;
        open_atomic_invariant!(inv.borrow() => perm => {
            result = x.load(Tracked(&perm));
        });
        Ok(result)
    } else {
        Err(())
    }
}
}

Its ensures clause promises out.unwrap() % 2 == 0. It can promise this because x.load returns a value that has to satisfy the EvenInv rule.

When the rule is broken

Change the operation to add 1 instead of 2. Verus rejects the program:

error: Cannot show invariant holds at end of block
   |
   | /     open_atomic_invariant!(inv => perm => {
   | |         x.fetch_add_wrapping(Tracked(&mut perm), 1);
   | |     });
   | |______^

Atomic invariants about two variables

An atomic invariant can be used to describe properties held by multiple shared variables together.

To see this, we look at another example: the tight window [lo, hi] of chapter 23, now with much more parallelism. Imagine that many threads are processing numbers and updating the two shared variables lo and hi concurrently. We want to prove that lo <= hi always holds, whatever order the threads run in. The complete program is in my_atomic_two_vars.rs.

As in the even-counter example above, we create lo and hi as PAtomicU64 instead of AtomicU64, so each is associated with a permission. Unlike the earlier example, the InvariantPredicate and the AtomicInvariant now have to account for two PAtomicU64 variables and two permissions.

So we define the K type to include two constant ids and the V type to include two permissions. This allows the inv function to express the relationship between the two variables: v.lo_p.value() <= v.hi_p.value().

#![allow(unused)]
fn main() {
pub struct K {
    pub lo_id: int,
    pub hi_id: int,
}

pub struct V {
    pub lo_p: PermissionU64,
    pub hi_p: PermissionU64,
}

// A permission is linear: each one lives in exactly one invariant, so we cannot also
// give `lo` or `hi` its own separate invariant. Properties of a single variable
// (e.g. `lo <= 100`) are simply extra clauses in this joint predicate.
pub struct WindowInv;

impl InvariantPredicate<K, V> for WindowInv {
    open spec fn inv(k: K, v: V) -> bool {
        &&& v.lo_p.id() == k.lo_id
        &&& v.hi_p.id() == k.hi_id
        &&& v.lo_p.value() <= v.hi_p.value()  // the relation between the two variables
    }
}

type Inv = AtomicInvariant<K, V, WindowInv>;
}

This two-variable invariant is used in the same way as the one-variable invariant. Whether a thread updates both variables or just one of them (e.g., only lo in widen_down and only hi in widen_up), it needs to open the invariant to get the permission or permissions.

#![allow(unused)]
fn main() {
// One physical step (fetch_min on lo), so one open/close of the invariant.
pub fn widen_down(lo: &PAtomicU64, Tracked(inv): Tracked<&Inv>, n: u64)
    requires
        inv.constant().lo_id == lo.id(),
{
    open_atomic_invariant!(inv => v => {
        lo.fetch_min(Tracked(&mut v.lo_p), n);
    });
}
}

widen_up is the same, with fetch_max on hi. Both fetch_min and fetch_max are atomic APIs that update the atomic variable in one atomic step. They make sure that the new value of the atomic variable is the smaller (for fetch_min) or the larger (for fetch_max) of the original value and the parameter. Each operation opens the same shared atomic invariant. Its contents v hold both permissions, and the operation uses just one of them (v.lo_p here). When the block closes, Verus checks the rule lo <= hi.

An operation that does both, widening the window to contain v, is just the two steps in order:

#![allow(unused)]
fn main() {
pub fn widen(lo: &PAtomicU64, hi: &PAtomicU64, Tracked(inv): Tracked<&Inv>, v: u64)
    requires
        inv.constant().lo_id == lo.id(),
        inv.constant().hi_id == hi.id(),
{
    widen_down(lo, Tracked(inv), v);
    widen_up(hi, Tracked(inv), v);
}
}

This widen function performs two atomic steps. At most one of them changes anything (if v is below lo, it is also below hi), so from the outside it looks like one step. Since we only need to prove lo <= hi and each atomic step preserves it, we do not need to reason about which step changes a shared variable.

Reading both variables

With two variables there is one thing you cannot do: read both in a single atomic step. No atomic instruction reads two variables at once, so a program that loads lo and then loads hi cannot claim anything about the pair: another thread may have changed one of them in between. (Of course, once all threads have finished updating, reading both would be fine. But to let Verus know that all the threads are done, we need a proof tool such as FracGhost, a kind of PCM, which chapter 25 introduces.) What we can prove here is a claim in proof mode, as a fact about the two permissions, by opening the atomic invariant inside a proof block:

#![allow(unused)]
fn main() {
    // Exec code cannot read two atomics in one atomic step, so the relation is stated
    // about the ghost permissions, in proof mode, by opening the invariant there.
    let Tracked(credit) = vstd::invariant::create_open_invariant_credit();
    proof {
        open_atomic_invariant_in_proof!(credit => inv.borrow() => v => {
            assert(v.lo_p.value() <= v.hi_p.value());
        });
    }
}

This statement is true, but weaker than in the single-variable case: it is about the proof-only permissions, not about two numbers the program holds. Section 24.2 shows how a lock gives you a statement about real values.

Small notes

  • Namespaces. The number given to Inv::new (the 1 above) is a namespace. Verus uses it to forbid opening an atomic invariant while it is already open, which would let one thread hold the permission twice. It only matters when atomic invariants nest, so you can pick any number for now.
  • Why Arc<Tracked<Inv>>. Threads need to own what they share, so the atomic invariant goes in an Arc like the variable. In chapter 25 we will use Shared, vstd’s tracked equivalent.
